## 自检清单

提交 UX 文档之前逐项检查：

**第 1 节**

- [ ] 每个障碍都有「代价」描述（不解决会损失什么）
- [ ] 障碍用具体场景描述，不用抽象术语
- [ ] OUT 的每条都标注了原因（交给谁 / 留到什么时候）
- [ ] 约束表格有三列（约束 / 来源 / 对设计的影响）

**第 2 节**

- [ ] 信息架构是空间树，不是功能列表或流程图
- [ ] 信息架构只包含用户真实可到达 / 可停留的位置，没有把技术过程默认写成位置
- [ ] 每条路径的步骤表格有四列（用户做了什么 / 注意力 / 系统响应 / 异常）
- [ ] 「注意力」列是认知焦点描述，不是 UI 元素名
- [ ] 每条路径末尾有路径外异常汇总
- [ ] 异常来自用户行为、产品决策或技术约束，没有默认补同步、冲突、失效、撤销等机制
- [ ] Journey 数量和 1.1 的障碍数量一一对应

**第 3 节**

- [ ] 每个界面只列用户真实会感知的状态，没有机械套用加载态 / 错误态模板
- [ ] 组件描述分「构成」和「交互行为」两部分
- [ ] 构成中说明了每个元素的显示条件
- [ ] 过渡意图用用户感知描述，不只是动效参数

**第 4 节**

- [ ] 数据边界覆盖三个维度：空 / 极长 / 极多
- [ ] 每个数据变更操作都有可逆性判断
- [ ] 不可逆操作的确认弹窗文案说明了具体后果
- [ ] 状态恢复逐项说明了「恢复哪些维度」
- [ ] 没有在缺少产品或技术依据时替系统设计草稿、撤销、同步冲突等机制

**第 5 节**

- [ ] 每条验收条件有判断方式
- [ ] 每条条件可以回答「是 / 否」
- [ ] 每个障碍对应至少 3 条验收条件
- [ ] 已定义的边界场景有对应的验收条件（不只验证 happy path）
- [ ] 验收条件没有验证 UX 文档未定义的技术机制
- [ ] 有独立的通用验收条件
