# Skill：写 User Journey

## 这个技能是什么

翻译出用户意图之后，还不能直接开始设计产品。

因为意图只说明「他想得到什么」，还没有说明「他是在什么情况下追求这个结果的」。

**写 User Journey**，就是把抽象意图落到一个真实、高频、可被团队共感的场景里。它的作用不是画流程图，而是把用户当时的处境、操作路径和成功标准写清楚。

---

## 为什么这一步容易出错

很多人一写 Journey，就会写成系统流程：

- 用户进入页面
- 点击按钮
- 查看结果
- 完成任务

这不叫 Journey，这叫页面操作说明。

Journey 的核心不是「系统发生了什么」，而是「这个用户当时为什么这样做，他在过程中哪里会顺、哪里会卡、他完成之后到底算不算成功」。

如果这里写空了，后面的产品设计就会脱离真实场景，变成凭空拼模块。

---

## 怎么做：写清三段

每条 Journey 都必须包含三段，而且顺序不能乱。

**① 用户处境**

先交代清楚这个人是谁，以及他为什么现在要做这件事：

- 他是谁，对这件事熟不熟
- 他刚经历了什么，现在处于什么状态
- 他知道什么，不知道什么

**② 任务路径**

再写他自然会怎么完成这件事：

- 他会从哪里进入
- 他会依次做什么
- 他会在哪里停顿、犹豫、分叉或返回

**③ 成功标准**

最后写完成之后，对用户来说什么叫“真的跑通了”：

- 他得到了什么结果
- 他的感受是什么
- 什么现象说明这条 Journey 已经成立

---

## 练习：什么叫一条有效 Journey

看下面这两种写法的区别：

**❌ 无效写法**

> 用户进入简历页面，点击筛选，查看推荐候选人，打开详情，完成筛选。

这只是动作串联，团队无法从中判断：

- 用户为什么会来这里
- 他有没有时间逐份精读
- 哪一步最可能卡住
- 怎样才算“完成得足够好”

**✅ 有效写法**

> HR 今天需要处理某个职位新进来的 20 份简历。  
> 他对岗位要求很熟悉，但没有时间逐份精读。  
> 他希望先在列表里快速判断大多数候选人，只有少数拿不准的再点进详情。  
> 如果他离开列表前，大多数简历都能完成初筛，而且下次回来状态清晰，这条 Journey 才算跑通。

这段话一出来，产品判断就会立刻不同。

---

## 一个完整示例

**Journey：HR 在简历列表中完成初筛决策**

**用户处境**

- HR 今天需要处理某个职位新进来的 20 份简历
- 他对岗位要求很熟悉，但没有时间逐份精读
- 他想快速判断哪些值得约面试，哪些直接淘汰

**任务路径**

- HR 打开该职位的简历列表，看到每份简历旁边已有匹配分析和推荐理由
- HR 扫描匹配点和主要差距，对大多数简历在列表层直接做出决定
- 遇到拿不准的简历，HR 点开详情查看更多信息，再回到列表继续处理
- 处理完一批后，HR 离开列表，候选人状态已全部更新

**成功标准**

- HR 不需要离开列表就能完成大多数初筛决策
- 系统给出的匹配分析让 HR 判断更快，而不是增加阅读负担
- HR 离开后，所有操作有记录，下次回来状态清晰

## 输出格式

写完之后，用下面这个格式整理：

```md
Journey：[一句话写清这是哪个高频场景]

用户处境

- [用户是谁]
- [他当前处于什么状态]
- [他知道什么，不知道什么]

任务路径

- [他自然会从哪里进入]
- [他会依次做什么]
- [哪里可能卡住、分叉或返回]

成功标准

- [任务完成时他得到了什么]
- [他的感受是什么]
- [什么现象说明 Journey 跑通]
```

## 自检：两个判断标准

写完每条 Journey，问自己两个问题：

**① 这是一个高频场景，还是一堆场景的混合物？**

如果一条 Journey 里同时出现“初筛”“约面”“统一管理候选人进度”，那说明写杂了。

**② 读完之后，团队能感受到用户当时的处境吗？**

如果不能，后面的设计就只能靠猜。

---

## 常见错误模式

**错误一：把 Journey 写成页面操作路径**

> ❌ 用户点击列表，进入详情，点击返回

这只说明界面，不说明用户为什么这样做。

**错误二：把多个频率不同的场景塞进一条 Journey**

> ❌ 既写日常高频处理，又写偶发异常处理

这样会直接把产品边界写乱。

**错误三：成功标准写成功能描述**

> ❌ 页面支持查看推荐理由

这不是成功标准，这是功能陈述。成功标准必须站在用户视角写。
