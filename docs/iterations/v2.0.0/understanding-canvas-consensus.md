## C1 模块形态

**结论**：

- 顶层模块「理解画布」（路由 `/understanding-canvas`），「心智模型 / Mental Model」不作为产品正式概念。
- 左栏：画布列表（新建 / 重命名 / 删除，按更新时间排序）。
- 主区工作区：
  - 顶部工具栏极简：画布标题、理解库（开右侧面板）、文本卡 / 矩形 / 圆形（可拖拽 icon）。
  - 画布左下工具栏：放大 / 缩小 / 适应视图 / 演示模式。
  - 画布右下：缩略图（minimap）。
  - 画布内搜索（Cmd/Ctrl+F 浮层，结果平移定位）。
  - 右侧单面板（互斥切换）：理解库模式 / 理解详情模式。
- 删除画布：硬删除 + 确认对话框（v1 不进回收站）。

**理由**：工具栏与控件尽量下沉到画布本体，保持顶部极简；右侧单面板避免多面板并存的心智负担。

**来源**：工具栏/面板多轮讨论（"顶部工具栏不需要那么多操作""右侧不用并存，只有一个""画布左下/右下归位"）。

**落点**：PRD 模块二（画布工作区）、实现设计模块总览。

## C2 元素体系

**结论**（五类元素，`kind` 判别）：

| 元素     | 关键要求                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 理解卡   | 引用理解库（非副本，可进多画布）；显示正文全文（不截断）、尺寸可调；画布上只读，点击开详情；被引理解删除后显示「（已删除）」占位 |
| 文本卡   | 支持简单 Markdown，双击就地编辑，失焦保存；仅支持拖拽创建（不支持点击）                                                          |
| 图形元素 | 矩形 / 圆形，工具栏 icon 拖拽创建；用于画布内标记；无文字标签                                                                    |
| 组       | 可命名容器（显式边框 + 标题栏）；元素拖入入组、拖出出组；拖组时组内元素跟随；删除组 = 解组（组内元素保留）；可嵌套               |
| 画布引用 | 引用另一张画布（显示其标题），点击跳转；目标被删显示占位                                                                         |

**理由**：画布参照"云文档画板"的元素体系——理解卡只是元素类型之一，文本卡是自定义元素；组必须有显式视觉（用户明确要求"组的样式要显示地展示出来"）。

**来源**：元素类型讨论、"画板的卡片可以自己改尺寸，没有截断，只有正文""文本卡仅拖拽""打组 + 组名 + 显式样式"。

**落点**：PRD 模块三（元素体系），实现设计 F3-F5、F16、F17、F21。

## C3 连线

**结论**：

- 有向连线（端口拖出），方向箭头从源指向目标。
- 自由文本标签：双击连线内联编辑（工具栏不放标签输入框）；标签随连线移动；持久化。
- 同一对卡片允许多条不同标签的连线。
- 连线吸附元素边界 + 自动绕行（重路由）。
- **连线样式（EdgeStyle，社区四维模型）**：
  ```ts
  EdgeStyle = {
    routing?: "straight" | "curve" | "orthogonal";  // 拐点类型（用户点名补充）
    lineStyle?: "solid" | "dashed" | "dotted";
    color?: string;      // 预设色板 key / hex
    width?: "thin" | "medium" | "thick";
    arrowhead?: "arrow" | "block" | "none";
  }
  // 默认：straight + solid + 灰 + medium + arrow
  ```
- 样式持久化、可重置默认。

**理由**：连线样式是关系语义的第二层表达（实线=确定、虚线=存疑、颜色=关系类型），缺了它连线的表达力少一半；拐点类型（直线 / 贝塞尔 / 正交）是社区连线样式的独立维度（draw.io / Miro / React Flow / X6 一致）。

**来源**：连线样式调研（用户指出漏了样式、再指出漏了拐点类型）。

**落点**：PRD M4-1~M4-7、服务端设计 EdgeStyle、实现设计 F7/F8/F18/F24。

## C4 编辑体验（基础体验做全）

**结论**：

- 参考线对齐（拖动时吸附边缘 / 中心）。
- 撤销 / 重做：仅键盘（Cmd/Ctrl+Z / Shift+Z），无工具栏按钮。
- **CAD 框选逻辑**：左→右拖拽 = 完全包含才选中（window）；右→左拖拽 = 相交即选中（crossing）。
- 框选多选、Shift 追加、整组拖动。
- 元素锁定（防误拖，`locked` 列）。
- 删除：Delete / Backspace + 确认，级联删连线。
- 画布内搜索、演示模式、PNG 导出。

**理由（重要原则）**：**基础体验是质量下限，永远不嫌多，与性能优化同一逻辑**——参考线、CAD 框选、锁定、搜索、导出这些"基础体验"不做 minimalism；minimalism 只约束价值主张（见 C10）。

**来源**："参考线我们也是要做的，这是基础编辑体验，你不能漏掉""框选采用 CAD 的 selection 逻辑""基础体验永远不嫌少，就跟性能优化是一个逻辑"。

**落点**：PRD 模块七、实现设计 F9-F15、F18-F23。

## C5 数据设计

**结论**：

- **存储范式：关系表（范式二）**，三张表：`understanding_canvases` / `understanding_canvas_elements` / `understanding_canvas_edges`。
- **优雅 schema 原则：共享列 + 引用 FK 列 + props JSON**：
  - 共同字段（x/y/width/height/z_index/locked/parent_id/时间戳）→ 列（需排序 / 索引 / 约束）。
  - 跨实体引用（`understanding_id` / `canvas_ref_id`）→ 引用 FK 列（需要 FK 完整性 SET NULL 占位 + 可查询"哪些画布用了理解 X"）。
  - kind 专属载荷（文本内容、组名、图形类型）与连线样式 → `props` JSON（从不被 SQL 查询，新增 kind / 样式字段无需迁移）。
- 增量写回（拖一次卡只改 x/y）；元素 / 连线 id 与 X6 cell id 一致。
- `canvases.updated_at` 随任何子变更联动（列表按最近活跃排序）。
- 迁移：v2.0.0 代码迁移（`CREATE TABLE IF NOT EXISTS` 幂等）。

**理由**：社区实践调研（Excalidraw / tldraw 文档快照 vs CollabBoard / 图编辑器关系表）——我们的场景（元素承载外部理解引用、需要 FK 完整性、需要查询）明确属于关系表路线；props JSON 是 tldraw 式"共享几何 + type 载荷"的验证模式。

**来源**：表结构两轮讨论（"社区怎么存""Schema 怎么设计比较优雅"）、社区调研。

**落点**：服务端设计 §1-§2。

## C6 双链与画布的关系

**结论**：

- **分层共存，不是同一件事**：
  - 双链（wiki-link / Connection）= 引用网：「我提到过 X」，弱引用、无向无类型、正文自动解析、全局、服务回溯来源。
  - 画布连线 = 结构网：「X 在我的结构里处于什么位置」，强语义、有向带标签带样式、用户显式搭建、画布局部、服务看清结构。
- **素材互通、数据不互通**：
  - 拖理解卡进画布时提示该理解已有双链（参考现有引用决定如何连线，但连不连、标签是什么由用户定）。
  - 理解详情显示「该理解出现于哪些画布」（M6-6，反向查询）。
  - 正文引用不自动画线；画布连线不写回 `understanding_connections`。
- **不能统一**（Scrintal 式）：画布连线是画布局部的——同一对理解在不同画布可标不同关系，统一成全局关系必然冲突。
- **不能纯视觉分离**（Obsidian 式）：我们的连线承载语义，放弃语义等于放弃画布核心价值。

**理由**：社区调研三种模式（Obsidian 分离 / Scrintal 统一 / Heptabase 部分统一）——我们选 Heptabase 式"分层 + backlink 导入白板做视觉整理"（与我们"拖卡提示已有双链"同构）；同时"画布局部"特性排除了统一方案。

**来源**：双链关系讨论 + 社区调研。

**落点**：PRD §1.5（与双链的关系定位）、服务端设计 `listCanvasesByUnderstanding`、实现设计 M6-6。

## C7 Agent 协作主张（核心心智与产品主张）

**结论**：

- **AI 是提案者，用户是裁判者**：灵感引擎从用户转移到 AI，用户从"发作者"变"裁判"。
- 旧流程的痛点：摆卡片 → overview → 等"迸发心智"→ 自己连线——最难的认知劳动压在用户身上；AI 的关联活在对话里不可见（"脑子是糊的，没有一个地方看关联关系"）。
- **协作主线**：
  ```
  ① 孤岛阶段：画布摆卡片 / 理解库散落理解
  ② 线头输入：用户带模糊直觉（"这个是不是就是那个"）
  ③ AI 提案：读当前画布 + 线头 + 已有上下文，推荐心智结构（带理由）
  ④ taste 诊断：用户判断对 / 不对 / 哪里不对，迭代修正
  ⑤ 认可落画布：AI 更新画布（增 / 连 / 分组）或用户手动拖卡连线，两条路径并存
  ```
- 两种协作入口并存：对话侧沉淀（全局 Chat 深聊后把关联沉淀成画布）/ 画布侧就地协作（画布里开 Chat 侧边栏，AI 以当前画布为作用域）。
- 设计含义：核心动作是"推荐心智模型"不是"整理画布"；提案输入 = 当前画布 + 线头；认可后改现有画布不新建；提案必须可见可诊断（结构预览 + 理由 + 可反驳）；判定标准 = 用户只需线头 + taste 验收。

**理由**：用户 Obsidian Canvas 真实体验 + 生产对话反推；判断（taste）是用户最擅长、AI 最不该代劳的，与产品原则完全对齐。

**来源**：多轮协作形态讨论（"AI 把我推着走""我用 taste 诊断""不靠突然迸发灵感"）。

**落点**：PRD §1.4（画布 × Agent 的协作主张，完整版）。

## C8 Agent 引用画布（cite canvas）

**结论**：

- Agent 回答中可引用画布，格式 `[[cv:<id>]]`（与其他实体引用同一体系）。
- **点击不跳路由，打开只读 Modal 展示画布元素**（元素 / 连线 / 标签，readonly view）。
- 只读 Modal 复用同一 CanvasGraph 渲染组件（`interactive: false`），与 canvas_sketch 提案预览共用——一个组件两个用途。
- 引用进入 v2.0 版本（不后置到 v1.x）。
- 全链路：`AgentContextRef` 加 `canvas` 态 → citations → entity catalog → 消息渲染 → 点击弹 Modal。

**理由**：Agent 读画布结构后回答中引用画布，是"结构可见"主张的自然延伸；不跳路由是因为画布没有"详情页"，只读 Modal 是查看的最小动作；与其他实体（understanding / context / domain）的引用体验保持一致。

**来源**："Agent 回答是否可以 reference 画布？……点击不要跳转到路由，要开一个 modal 去展示画布元素（readonly view）"。

**落点**：服务端设计 Agent tool 清单、实现设计只读 Modal 组件。

## C10 设计原则

**结论**：

- **基础体验 vs 价值主张是两个不同范畴**：
  - 基础体验（搜索、导出、撤销、锁定、缩放、框选、样式、minimap、演示……）= 质量下限，**永远不嫌多**，与性能优化同一逻辑。
  - 价值主张（协作主张、tool、引用、素材桥）= 产品内核，**需要克制、carefully designed**，每个都要挣得位置。
- **minimalism 只约束价值主张，不约束基础体验**——把基础体验当价值主张砍（如砍搜索/导出）和把臆测当价值主张加（如对话实体清单、Search 结构上下文、Domain 双视角、提案关系预演）都是错的。
- 臆测性功能一律砍掉，等真实痛点出现再 carefully design。
- 现阶段产品影响最小化：画布作为独立新模块接入，现有模块机制零改动；唯一新增桥是 M6-6；概念定位（Domain=归类 / Understanding=原子 / Context=素材 / Connection=引用网 / Canvas=结构）写清楚但不做 UI 整合。

**理由**：用户明确纠正（"基础体验是永远不嫌少的""你有点 over design 了，我是个 minimalist""所有的功能都应该 carefully designed"）。

**来源**：多轮原则纠偏。

**落点**：本文档即原则的记录；后续所有功能决策以此为准。

## C11 技术选型

**结论**：

- **画布引擎：AntV X6（@antv/x6 3.x，MIT）** + `@antv/x6-react-shape` 渲染 React 卡片。
- Spike 全部验证通过：React 19 兼容（createRoot）、卡片渲染、带标签有向连线、参考线、撤销重做、DnD 拖入、打组（embedding，`addTo` 双向）、图形元素、minimap、快照 round-trip。
- **排除 tldraw**：v4+ 默认仅开发许可，生产需 license key（商业收费 / hobby 非商业 + 水印 / 无 key 属于未授权 + 水印按钮 + 判定漏洞升级即白屏）；"MIT 应用"不豁免库的许可。
- AntV 性能问题澄清：X6 的 SVG 大规模性能问题（600+ 节点变慢）不适用于本场景（画布 5-50 卡）。
- 关键实现要点：运行时需 `tslib`；插件全在核心包；History 是插件（`graph.use(new History(...))`）；`dnd.start` 传节点实例；embedding 用 `addTo`（`setParent` 只设单向）；交互拖组时子元素自动跟随。

**理由**：能力最强且 MIT；tldraw 许可不可接受；React Flow 缺参考线 / 撤销重做需自研。

**来源**：多轮选型讨论 + spike 验证（14/14 + 9/9 + minimap）。

**落点**：实现设计 §2、spike 结论。

## C12 否决项（明确不做）

| 否决项                                                                | 理由                                                                                                                           |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 画布 draft / published 状态机                                         | "成型度"是光谱不是布尔（违认知保真）；结构本身就是信号（模型应会推断）；draft/publish 隐含内容发布工作流，不适用于个人思考画布 |
| Agent 直接对画布 CRUD（无审批）                                       | 违背"关系来自用户显式标记"；布局操作是伪需求                                                                                   |
| 对话侧实体关系视图 / Search 结构上下文 / Domain 双视角 / 提案关系预演 | 臆测性价值主张，不是主张的必然延伸                                                                                             |
| AI 自动生成关系网并入库                                               | 产品原则红线                                                                                                                   |
| 多人协作 / 评论 / 投票 / AI 生成图表 / 自由画笔                       | 本地单机；"用户是大脑"                                                                                                         |
