# Reflecta PMF MVP Scope

> 日期：2026-06-10
>
> 状态：Current
>
> 职责：定义 PMF MVP 的范围、核心对象、Core / Support / Later / Never 和验收标准。页面展示和交互细节见 `domain-workspace-product-spec.md`。

## MVP 目标

PMF MVP 要验证：

> 用户能否把一次学习、实践或对话后的有效思考，沉淀成可追溯的个人理解；长期回看时，能否如实看到自己在某个领域里的理解、Context和显式关系。

MVP 不是 AI 产品，也不是图谱产品，而是：

> 一个能让个人理解带着Context和关系长期生长的最小系统。

## 核心对象

### Understanding：个人理解

Understanding 是用户形成的一个个人理解，不是普通Understanding条目。

它可以是：

- 判断：我现在相信什么。
- 触动：某个材料为什么击中了我。
- 困惑：我意识到一个还没想清的问题。
- 教训：一次实践后我学到了什么。
- 模型雏形：我开始看见某类问题的结构。

规则：

- Understanding 必须由用户主动创建或确认。
- Understanding 可以暂时没有 Connection。
- Understanding 可以被后续修改，因为理解会随经历和回看修正。

### Context：理解的Context

Context 是这个理解从哪里长出来。

它可以来自个人实践、书籍、视频、文章、他人观点、AI 对话、项目经历、交易复盘等。

规则：

- 一个 Understanding 可以有多个 Context。
- Context 应尽量保留“为什么触发我”，而不是只保留 medium。
- Context 可以后续补充、修改或删除。

### Domain：领域语境

Domain 是用户回看某个领域理解的语境。

它回答：

> 我在这个领域已经形成过哪些理解？

规则：

- Understanding 可以归属一个或多个 Domain。
- Domain 用于沉淀时放入语境，也用于回看时盘点领域理解。
- MVP 不要求复杂领域体系，但必须支持用户按领域回看。

### Connection：用户显式意识到的理解关系

Connection 是用户显式表达的理解关系。

规则：

- Connection 不应由 AI 自动创建并直接入库。
- AI 建议关系属于 PMF Later，且必须由用户确认。
- Connection 可以后续增加、调整或移除。

## 核心用户路径

### Journey A：沉淀个人理解

用户刚经历一次学习、实践、观察或对话，并意识到其中有一个值得留下的个人理解。

路径：

1. 进入沉淀入口。
2. 用自己的语言写下理解。
3. 记录这个理解从哪里来。
4. 放入一个领域语境。
5. 如果当下意识到它和已有理解有关，连接已有理解。
6. 如果暂时没有意识到关系，独立保存。
7. 保存后，这条理解进入长期知识网。

### Journey B：回看领域理解

用户一段时间后回到某个领域，想知道自己已经理解了什么。

路径：

1. 进入某个领域语境。
2. 看到该领域下已有的个人理解。
3. 看到每个理解从哪里来。
4. 看到理解之间已显式建立的关系。
5. 区分哪些理解已经连接，哪些暂时独立。

### Journey C：后续整理和修正

用户回看时产生新的理解，发现旧理解需要补充、修正或连接。

路径：

1. 打开已有理解。
2. 修改理解表达。
3. 补充或修正Context。
4. 补充与其他理解的关系。
5. 调整或移除不再成立的关系。
6. 保存后，知识网结构随之更新。

## Core Features

| Feature          | 对应 Job                                    | 为什么是 Core                                    |
| ---------------- | ------------------------------------------- | ------------------------------------------------ |
| 个人理解记录     | 用户用自己的语言写下一个理解                | 没有它，产品无法承载“个人理解”                   |
| Context记录      | 用户保留这个理解从哪里来                    | 没有它，理解会退化成抽象结论                     |
| 领域归属         | 用户把理解放进以后能回看的领域语境          | 没有它，长期回看无法形成“我对这个领域理解了什么” |
| 用户显式关系表达 | 用户在意识到关系时连接已有理解              | 没有它，知识网无法由用户理解自然长出来           |
| 独立理解保留     | 用户暂时没意识到关系时，理解也能独立存在    | 没有它，产品会强迫整理，违背自然积累             |
| 后续修正与补关系 | 用户回看后能修改理解、补 Context、补关系    | 没有它，知识网不能自然生长                       |
| 领域内回看       | 用户能回到某个领域，看已有理解              | 没有它，无法验证“聚沙成塔”                       |
| 个人知识网呈现   | 用户能看到理解、Context、显式关系构成的结构 | 没有它，只是记录工具，不是 Reflecta              |

## Core Feature 细节

### 个人理解记录

核心功能：

- 用户能创建一条个人理解。
- 用户能用自己的语言填写理解内容。
- 用户能保存后再次编辑。
- 系统允许理解没有关系时独立存在。

关键业务规则：

- 创建入口必须以“写下个人理解”为主，不得把用户首先带入复杂字段填写。
- 系统不得要求用户必须先选择关系才能保存。
- 系统不得自动把 AI 总结内容作为用户理解入库。
- 用户保存后，内容必须能在对应领域回看中出现。

### Context记录

核心功能：

- 用户能为一个理解记录Context。
- 用户能选择或填写Context medium，例如实践、书籍、视频、文章、AI 对话、他人观点。
- 用户能记录Context 标题或场景描述。
- 用户能记录“为什么这个Context触发了我”。
- 用户能后续补充、修改或删除Context。

关键业务规则：

- Context必须和某个个人理解关联。
- Context不应被设计成独立知识节点。
- Context 字段不应只停留在 medium；必须给用户保留具体场景和触发原因的空间。
- 用户可以先保存理解，再补充Context，但回看时应清楚看见哪些理解已有 Context、哪些Context较薄。

### 领域语境组织

核心功能：

- 用户能把个人理解放入一个或多个领域语境。
- 用户能创建、重命名、调整领域语境。
- 用户能在沉淀时选择领域。
- 用户能在回看时进入某个领域。

关键业务规则：

- 领域语境服务于回看“我对这个领域理解了什么”，不得只被设计成对象管理Domain。
- 用户可以先使用临时或较粗的领域语境，后续再调整。
- 一个理解可以归属多个领域。

### 用户显式关系表达

核心功能：

- 用户能在写理解时连接已有理解。
- 用户能在回看整理时补充关系。
- 用户能查看一条理解连接了哪些已有理解。
- 用户能移除或调整关系。

关键业务规则：

- 关系必须来自用户显式表达或用户确认。
- 系统不得自动创建关系并直接入库。
- 没有关系的理解必须允许保存。
- 关系表达不应被设计成每次沉淀必填的表单步骤。

### 后续整理和修正

核心功能：

- 用户能编辑已有个人理解。
- 用户能补充或修改Context。
- 用户能补充、修改或移除关系。
- 用户能调整领域归属。

关键业务规则：

- 后续修正是 Core，不是高级编辑功能。
- 用户修正内容后，回看视图和知识网呈现必须同步更新。
- 系统不得把旧内容锁死成不可更改的记录。

### 领域内回看

核心功能：

- 用户能进入某个领域，看到该领域下已有个人理解。
- 用户能看到每条理解的Context摘要。
- 用户能看到每条理解的显式关系摘要。
- 用户能打开某条理解查看完整内容、Context和关系。
- 用户能从回看中进入编辑 / 补 Context / 补关系。

关键业务规则：

- 领域回看必须服务“我在这个领域已经理解了什么”，不得退化成普通内容列表。
- 回看视图必须同时暴露理解、Context和关系三个层面。
- 不要求 MVP 自动识别薄弱点或生成领域总结。

### 个人知识网呈现

核心功能：

- 产品能呈现用户已沉淀的个人理解。
- 产品能呈现理解与Context的关系。
- 产品能呈现理解之间由用户显式表达的关系。
- 产品能区分已连接理解和独立理解。

关键业务规则：

- 知识网呈现的核心是如实反映，不是自动推断。
- 视觉形态可以是图谱、列表、局部关系视图或组合形态；本文不锁死 UI。
- 如果采用图谱，图谱必须服务理解、Context和显式关系的回看，不得只是视觉展示。
- 如果采用列表或领域视图，也必须保留关系和Context可见性，否则无法兑现知识网价值。

## Support Features

| Feature                 | 支撑什么                                   |
| ----------------------- | ------------------------------------------ |
| 查找已有理解            | 支撑用户在表达关系时找到要连接的已有理解   |
| 基础编辑入口            | 支撑后续修正、补 Context、补关系           |
| 基础浏览 / 过滤领域内容 | 支撑领域内回看                             |
| 持久保存与可靠数据结构  | 支撑长期积累，不创造核心认知价值但必须稳定 |

### 查找已有理解

支撑目标：

> 用户在表达关系时，需要找到要连接的已有理解。

功能要求：

- 支持按关键词查找已有理解。
- 支持在连接关系时快速选择已有理解。
- 搜索结果应显示足够上下文，避免用户连错对象。

### 基础编辑入口

支撑目标：

> 用户后续修正理解、补 Context、补关系。

功能要求：

- 用户能从回看路径进入编辑。
- 用户能从单条理解详情进入编辑。
- 编辑后回到原语境，不丢失当前位置。

### 基础浏览 / 过滤领域内容

支撑目标：

> 用户回看某个领域下已有理解。

功能要求：

- 支持按领域进入内容范围。
- 支持在领域内查看理解列表或结构。
- 可支持基础类型、时间或关键词筛选，但不作为 MVP 价值重点。

### 持久保存与可靠数据结构

支撑目标：

> 长期积累必须稳定可信。

功能要求：

- 用户创建、编辑、删除、连接关系后，数据可靠保存。
- 应避免关系、Context、领域归属出现明显丢失或不一致。

## PMF Later

| Later                       | 原因                                                         |
| --------------------------- | ------------------------------------------------------------ |
| AI 辅助澄清表达             | 贴近 value proposition，但手动沉淀和回看闭环要先成立         |
| AI 提醒补充Context          | 有助于提高沉淀质量，但 PMF 先验证用户是否愿意主动保留Context |
| AI 建议可能关系             | 有助于发现连接，但必须建立在用户主导关系之后                 |
| 自动识别薄弱理解            | 重要的下一阶段能力，但 MVP 先做到如实呈现知识网              |
| 心智模型聚合 / 领域结构洞察 | 贴近长期愿景，但需要足够沉淀数据作为基础                     |

## Non-goals / Never

| Never                                 | 原因                                               |
| ------------------------------------- | -------------------------------------------------- |
| AI 替用户自动生成“个人理解”并直接入库 | 违背“用户是大脑，AI 是辅助”                        |
| AI 自动构建关系网并直接当作用户知识网 | 关系必须来自用户显式理解                           |
| 强制每条理解填写关系                  | 会打断自然沉淀，也违背“孤岛不是错误”               |
| Context 管理后台                      | 用户目标不是管理Context 库，而是让每个理解有根     |
| 关系管理后台                          | 关系是理解的一部分，应在写理解或回看整理时自然补充 |
| 全局图谱主入口                        | 图谱可以是观察模式，但不定义 MVP 主路径            |

## 验收标准

MVP 成立时，用户应该能完成：

1. 我刚刚形成了一个理解，能用自己的语言写下来。
2. 我能记录它来自哪次学习、实践或对话，以及为什么触发我。
3. 我能把它放进某个领域。
4. 如果它和已有理解有关，我能自然连接。
5. 如果暂时没有关系，它也能独立存在。
6. 几天后我回看这个领域，能看到已有理解、它们的Context、以及我显式建立过的关系。
7. 我能修正旧理解、补 Context、补关系。

## PMF 验证指标

行为指标：

- 用户是否创建了多条个人理解。
- 用户创建个人理解时，是否愿意记录Context。
- 用户是否把个人理解放入领域语境。
- 用户是否主动建立显式关系。
- 用户是否回看某个领域。
- 用户是否在回看后修改理解、补 Context或补关系。

质性判断：

- “我对这个领域的理解是这些。”
- “这些理解分别Context于这些经历、材料和对话。”
- “有些理解已经连起来了，有些还只是独立存在。”
- “我能回头修正旧理解，而不是重新开始。”
