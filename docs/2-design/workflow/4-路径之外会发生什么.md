## 4. 路径之外会发生什么

第 2 节描述「用户正常走完路径时发生什么」，第 4 节覆盖「用户没有正常走完路径时，或路径之外的条件触发时发生什么」。两节共同构成完整的设计覆盖。

第 4 节不是技术兜底清单。这里只写用户能感知、且产品或技术前提已经成立的边界。不要因为“完整性”默认补上同步、冲突、失效、撤销、网络错误等机制；如果这些机制没有在产品决策或技术约束中出现，就不要把它们写进 UX 文档。

### 4.1 数据边界

#### 存在原因

设计师容易在理想数据下设计（3–5 条记录、标题长度适中），但用户的真实数据千差万别。数据边界提前定义极端情况下的处理方式，避免实现时布局崩塌。

#### 应该写什么

三个维度逐一穷举：

| 维度     | 覆盖场景                                           |
| -------- | -------------------------------------------------- |
| **空**   | 数据为零时（空列表、无 Context、无结果）           |
| **极长** | 单条内容超长时（标题极长、正文极长、单条内容极长） |
| **极多** | 数量极多时（列表超过 100 条、层级极深嵌套）        |

#### 格式

两列表格：`边界场景 | 处理方式`

#### 质量信号

✅ **好的写法**

- 空态不只说「显示空态」，还说明了具体的引导 CTA 和文案方向
- 极长内容说明了截断规则和用户如何访问完整内容
- 极多数量说明是虚拟滚动还是分页，以及筛选的优先渲染策略

❌ **常见错误**

- 只考虑理想数据，没有考虑极值
- 「显示空态」没有说明空态的具体内容
- 极长内容只说「截断」，没有说截断后如何访问完整内容

---

### 4.2 操作边界

#### 存在原因

操作有不同的可逆程度。把可逆性判断写清楚，能防止设计师对轻量操作过度设计（弹窗确认），或对不可逆操作设计不足（直接删除）。

#### 可逆性判断框架

| 可逆性         | 典型操作                       | 处理方式                           |
| -------------- | ------------------------------ | ---------------------------------- |
| **不可逆**     | 删除有子内容的对象             | 二次确认弹窗，弹窗文案说明具体后果 |
| **轻量操作**   | 删除双向链接引用、移除筛选条件 | 直接执行或轻量确认，按产品约定处理 |
| **实时可修改** | 编辑文本、修改分类             | 直接执行，无需确认                 |

如果产品已经明确支持撤销，再写 undo toast 等具体机制；如果没有，不要在 UX 文档中默认补撤销能力。

**不可逆操作的确认弹窗文案要求：**

- 说明具体后果，不只是「此操作不可撤销」
- ✅ 「删除后，该分类下的 N 条 Thought 将归入「[父节点名]」。此操作不可撤销。」
- ❌ 「确认删除？」

**特别需要覆盖「创建后立刻离开」的场景：**
用户新建内容后立刻跳走，内容可能未完成，需要明确这个产品里的处理方式。它可以是保留、丢弃空内容、作为普通内容留下，或交给产品决策补充；不要默认写成草稿恢复。

#### 格式

三列表格：`操作 | 可逆性判断 | 处理方式`

#### 质量信号

✅ **好的写法**

- 轻量操作的处理方式和产品机制一致，不凭空增加撤销能力
- 每个不可逆操作的弹窗文案都说明了具体后果
- 创建后立刻离开的策略和产品的数据模型一致

❌ **常见错误**

- 所有删除操作都用弹窗（对轻量操作过度保护）
- 确认弹窗只有「确认 / 取消」，没有后果说明
- 遗漏「创建后立刻离开」这种边界操作
- 在产品没有撤销机制时，默认写 undo toast

### 4.3 状态恢复

#### 存在原因

用户的使用不是线性的：他们会中断、返回、刷新、被打断。状态恢复定义了用户「重新回来时」的体验。良好的状态恢复让用户感觉「我在这里」，而不是「我在哪」。

#### 应该写什么

对每个用户可能「中断后返回」的场景，明确说明恢复哪些状态维度：

- 当前选中的位置 / 页面
- 搜索词 / 筛选条件
- 滚动位置
- 编辑中的内容（仅当产品明确存在未完成内容保留机制时）

**每个场景都要逐项说明恢复的维度，不能只写「恢复状态」。**

如果产品没有同步、冲突或草稿机制，不要写网络中断恢复、冲突处理、草稿恢复。UX 文档可以把这类缺口标成「待产品 / 技术确认」，但不能替它们做机制设计。

#### 格式

两列表格：`恢复场景 | 恢复策略`

#### 质量信号

✅ **好的写法**

- 恢复策略明确列出了「恢复什么」：
  > 「恢复：原 Category 选中状态 + 原筛选条件 + 原滚动位置（三者同时恢复）」

❌ **常见错误**

- 只写「关闭详情 → 返回列表」，没有说恢复哪些维度
- 把网络中断、同步冲突、草稿恢复当成默认必写项
- 在缺少产品或技术依据时，替系统设计恢复机制
