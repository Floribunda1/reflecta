## 3. 路径上每个节点的设计

### 3.1 每个界面的所有状态

#### 存在原因

界面不只有「一切正常」的状态。未穷举的状态是实现阶段最常见的设计遗漏来源，也是 QA 的高频缺陷区域。

#### 应该写什么

对信息架构中每一个用户可以停留的位置，列出用户真实会感知到的状态。状态不是固定模板，而是由产品形态、数据来源、技术约束和用户路径共同决定。

| 状态           | 说明                               | 注意点                                                       |
| -------------- | ---------------------------------- | ------------------------------------------------------------ |
| **空态**       | 内容为零时                         | 不能是空白；必须有引导 CTA                                   |
| **正常态**     | 有内容的默认状态                   | —                                                            |
| **交互子状态** | 正常态内部的变体                   | 如：正常态 → 搜索结果态 → 无结果态                           |
| **等待态**     | 用户确实需要等待系统完成某个过程时 | 只有当用户会感知等待时才写，说明等待期间界面如何保持空间稳定 |
| **不可完成态** | 产品已明确存在某类操作无法完成时   | 只有当产品或技术约束已明确时才写，说明用户看到什么、能做什么 |

写状态前先问两个问题：

1. 用户会不会真的看到或感知这个状态？
2. 这个状态是否来自产品决策、技术约束或第 2 节路径？

如果答案是否，就不要写。比如 local-first 应用不应该默认写 loading、error boundary、同步、冲突、失效、撤销等状态，除非这些机制已经被产品或技术明确纳入体验。

#### 格式

按界面分组，每组一个表格：`状态 | 触发条件 | 呈现方式`

#### 质量信号

✅ **好的写法**

- 空态有明确的 CTA，引导用户下一步
- 等待态只在用户确实需要等待时出现，并说明等待期间界面如何保持空间稳定
- 子状态层次清楚（搜索结果态是正常态的子状态，不混为一谈）
- 状态能追溯到第 2 节路径或第 1.3 的约束

❌ **常见错误**

- 机械套用空态 / 加载态 / 错误态模板，不判断产品是否真的存在这些状态
- 把技术异常当成 UX 状态写进去，但没有产品或技术依据
- 状态表格是功能描述：「用户可以搜索和筛选」是功能，不是状态

### 3.2 每个核心组件的构成和交互行为

#### 存在原因

3.1 描述「界面有哪些情况」，3.2 描述「这个元素本身是什么以及如何响应用户操作」。两者分开描述，避免混淆。

#### 应该写什么

对每个需要设计决策的核心组件（反复出现的、或交互复杂的）：

- **构成**：这个组件由哪些元素组成，以及每个元素的**显示条件**（不是所有元素都常驻）
- **交互行为**：用户可以对这个组件做什么，系统如何响应（按交互动作逐条描述）

#### 格式

每个组件一个小节：

- 「构成」用元素列表描述，说明显示条件
- 「交互行为」用 bullet list，格式：`[用户动作]：[系统响应]`

需要覆盖的交互动作类型：单击、双击、hover、右键、拖拽、键盘操作。只覆盖组件真实支持的动作，不为了完整性硬补不存在的交互。

#### 质量信号

✅ **好的写法**

- 构成说明了每个元素的显示条件：
  > 「操作入口：hover 时显示 More 菜单（删除 / 修改类型）」
- 交互行为覆盖了所有可能的用户动作，包括 hover 和 focus 状态

❌ **常见错误**

- 只写正常交互，遗漏了组件真实存在的 hover、focus、禁用等子状态
- 构成元素没有显示条件（「More 菜单」而不是「hover 时显示的 More 菜单」）
- 把业务规则写进组件描述（业务规则属于功能文档）

### 3.3 界面变化时用户的感知（过渡意图）

#### 存在原因

过渡不只是动效，更是用户的空间感知。错误的过渡会让用户感觉「迷失了」（不知道刚才在哪、现在在哪）。正确的过渡强化用户的空间模型。

设计师容易在线框图阶段忽略过渡意图，导致开发用默认动效填充，破坏设计意图。

#### 应该写什么

对每个重要的界面变化场景：

- **过渡场景**：什么变化触发了这个过渡
- **过渡意图**：用户在这次变化中应该感知到什么（停留在原地 / 进入新空间 / 内容展开 / 返回原位）
- **实现方式**：实现这个意图的具体方式

至少要覆盖：从列表进入详情、从详情返回列表、模态弹出和关闭、搜索/筛选触发列表更新。

#### 格式

三列表格：`过渡场景 | 过渡意图 | 实现方式`

#### 质量信号

✅ **好的写法**

- 过渡意图用用户感知描述，不是动效参数：
  > 「用户感知到自己处于同一工作台，内容在原地更新，没有跳页感 → 右侧列表 crossfade，不整页跳转」

❌ **常见错误**

- 只说实现方式，不说意图（不知道为什么要这样实现）
- 只写「进入」的过渡，遗漏「返回」的过渡意图（两者需要对称）
- 过渡意图只说「顺滑」（无法驱动实现判断）
