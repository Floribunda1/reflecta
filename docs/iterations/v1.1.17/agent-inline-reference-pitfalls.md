# Agent 正文引用踩坑记录

这份文档只记录正文引用 / mention 相关踩坑，不写新方案，不替当前实现背书，也不讨论和 mention 无关的问题。当前实现见 [Citation Architecture](agent-inline-reference-citation-architecture.md)。

## 0. 问题范围

用户想要的是：Agent 回复正文里能出现可点击的知识库实体引用。

这里的实体主要是：

- Understanding
- Context
- Domain

这份文档只记录“正文里怎么表达引用，以及这个表达怎么绑定到真实实体”这条链路上的坑。

## 1. 方案一：AI 直接在 content 里输出引用语法

这类方案让模型直接在正文里写一种可解析格式，前端或后端再 parse。

出现过或讨论过的形式包括：

- `[[type:title#id]]`
- `[[title#id]]`
- `<entity_ref type="understanding" entityId="..." fallbackText="..." />`
- 其他 JSON / YAML / markdown token 变体

当时想解决的问题：

- 正文里直接出现可点击引用。
- 引用里同时带标题和 id，前端 parse 后能渲染。

实际踩到的坑：

- Agent 输出不可靠，经常出现 title 和 id 对不上。
- 模型会把 A 的标题配到 B 的 id。
- 模型不一定稳定遵守同一种格式，这次写 XML，下次可能写 JSON、YAML 或 markdown。
- 格式没被 parse 时，用户会直接看到 raw 协议文本。
- 一旦这种协议进入历史消息，后续模型会继续复制它。

这个坑的核心不是某个 parser 写得不够强，而是模型正文输出本身不适合作为稳定机器协议。

## 2. 方案二：对本轮对话中出现的 entity 收集并分配 ref 编号

这类方案先收集本轮出现的实体，再分配一个模型可写的 ref，最后系统把 ref 映射回真实实体。

大致流程：

```text
本轮出现实体
  -> 系统分配 ref
  -> Agent 在正文里写 ref
  -> 系统把 ref 映射回真实 entity
```

这个方向踩过两类不同坑。

### 2.1 使用短编号，例如 `S1` / `S2` / `U1` / `D1`

当时想解决的问题：

- 比真实 id 短，模型更容易写。
- 不在正文里暴露真实 id。
- 看起来接近社区 numbered citations。

实际踩到的坑：

- Agent 有时候不会按 `[S1]` 这种格式写，而是直接输出 `S1`。
- 短编号太像普通文本，正文里不容易稳定区分“引用”还是“普通内容”。
- 模型会把短编号当成后续可复用身份。
- 用户下一轮也可能直接说“修改 S1”，系统会被迫解释这个短号来自哪一轮、还是否有效。

具体问题是：短编号本来只是本轮引用显示辅助，但很容易被模型和用户当成实体身份。

### 2.2 使用无意义编号，例如 `ref:nanoid`

当时想解决的问题：

- 避免 `S1` / `D1` 这种短编号太像自然语言。
- 避免短编号和正文普通内容混淆。
- 用随机 ref 代表本轮实体映射。

实际踩到的坑：

- Agent 会以为 `ref:nanoid` 就是真实 entity id。
- Agent 调用 tool 时会一直用这个 `ref_id` 传参。
- 工具参数链路开始被 display ref 污染。
- 历史里一旦出现这些 ref，恢复和后续上下文都要解释它们。

具体问题是：无意义 ref 虽然不像自然语言，但更像一个真实系统 id，反而更容易误导 Agent 在工具调用里继续使用。

## 3. 方案三：title 自动匹配

这类方案让 Agent 只输出普通标题，系统在正文里扫描标题并自动替换成实体引用。

这个方案在方案阶段就被否定，没有继续实现。

被否定的原因：

- 有些笔记标题可能只有一个字。
- `AI`、`产品`、`设计` 这类标题和普通正文词重合度极高。
- 同名、别名、旧标题、父子 Domain 都会制造歧义。
- 模型写出一个标题，不代表它一定想引用那个实体。

这个方向的问题很早就明确了：错绑的风险太高。

## 4. 方案四：历史 Final Answer Object Generator / finalizer 二次全文生成

历史实现大致是：

```text
Pi Agent 先生成普通答案
  -> Reflecta finalizer 再读一遍答案、toolResults、entityCatalog
  -> finalizer 输出 JSON parts
  -> 前端显示最终 parts
```

当时想解决的问题：

- 不再让主 Agent 在正文里手写 `[[...]]`、XML、JSON、YAML 之类引用格式。
- 让最终答案变成结构化 parts。
- entity id 可以经过 catalog 校验。

实际踩到的坑：

- 这个方案概念上不清晰：它到底是“引用绑定器”，还是“第二个回答生成器”。
- 实际运行时它变成了第二个回答生成器，会重写正文。
- 主 Agent 已经写完答案后，用户还要等 finalizer 再生成一次。
- test 最新日志里，主模型约 44s 已经写完，finalizer 又追加约 17s。
- finalizer 输入还带完整 `toolResults`，最新 test 工具结果约 8.1 万字符，导致二次生成明显变慢。
- JSON mode 只解决“输出是不是 JSON”，没有解决“引用是不是放在正文正确位置”。
- 即使 schema 通过，也可能只是在末尾补几个 `entity_ref`，正文里的关键实体仍然没有引用。
- 最新 test 里最终 parts 只有 5 段：前 3669 字是普通 text，末尾 4 个 domain `entity_ref`；正文里的高质量 Understanding 标题没有变成引用。
- 因为等待 finalizer，有 catalog 的回答不会直接展示主模型正文流，体验比之前慢。

这个方案目前最大的问题不是某个参数没调好，而是职责混在一起：它一边想做结构化引用，一边又在重写整篇答案。

## 5. 当前记录到的共同现象

上面几类方案表现不同，但反复出现过这些现象：

- 模型把显示用 token 当成真实身份。
- 模型把标题和 id 配错。
- 模型不稳定遵守正文里的引用格式。
- 短号或 ref 一旦进入历史，就会影响下一轮。
- title 自动匹配会在标题很短或很泛时误绑。
- 二次 finalizer 会拖慢输出，并且不保证引用真的落在正文关键位置。

这些只是已经踩过的坑记录。当前主路径已经改为 numbered citation，不再保留 finalizer / structured parts 作为运行时方案。
