> 当前共识：PMF MVP 的主产品形态采用 **Domain Workspace**。Reflecta 不再被理解为“Capture 页面 + Contemplate 页面”两个强分离工作区，而是一个按领域组织的个人理解工作台。用户进入一个领域后，在同一语境里完成看已有理解、写新理解、补来源、补关系、修正旧理解、观察局部关系。
>
> 当前保留意见：本文仍不锁死最终视觉 UI。卡片、列表、outline、局部图谱的组合方式，以及具体布局密度，后续仍需 UX 设计推敲。

---

## 1. 核心形态

Reflecta PMF MVP 的推荐形态是：

> **Domain Workspace：以领域为入口，以理解卡片 / 条目为主体，以来源和局部关系为详情，以图谱作为辅助观察模式。**

它想传达的使用效果是：

> 用户打开一个领域，就像打开自己的小型研究现场。这里摆着自己已经形成过的理解。每个理解都不是普通笔记，而是一个曾经想明白过的点；它能追溯到具体来源，也能看到和其他理解的显式关系。用户可以在这里继续写、看、改、补来源、补关系。

这个形态比“写作页面 + 图谱页面”更贴近 value proposition。因为用户真正要完成的不是先选择功能，而是在某个领域语境里持续让个人理解生长。

---

## 2. 用户心智

Domain Workspace 不应该发明全新的操作模型。目标用户大概率熟悉：

- PKM / 笔记工具：领域、列表、详情、引用、backlinks。
- IDE / 文件浏览式工作流：左侧定位，中间浏览，右侧停下来编辑。
- 双向链接工具：在正文中自然引用已有内容，之后回看关系。
- 图谱工具：观察关系结构，但不是每次写内容的默认入口。

因此，MVP 应复用这些心智：

- 左侧是领域导航。
- 中间是当前领域里的理解卡片 / 条目。
- 右侧是选中理解的详情、来源和局部关系。
- 图谱是当前领域内的辅助观察视图，不是主入口。

---

## 3. 主界面结构

Domain Workspace 使用一个主工作台承载核心闭环。

```text
┌──────────────────────────────────────────────────────────────┐
│ 左侧：领域导航                                                │
│ - 交易心理                                                    │
│ - AI / Agent                                                  │
│ - 产品设计                                                    │
│ - 认知哲学                                                    │
├──────────────────────────────────────────────────────────────┤
│ 中间：当前领域的理解卡片 / 条目流                              │
│                                                              │
│ [止损即承认错误]                                              │
│ 来源：一次爆仓复盘                                            │
│ 关系：连接到「亏损和自我失败绑定」                              │
│                                                              │
│ [FOMO 源于社交比较]                                           │
│ 来源：盘中追单经历                                            │
│ 关系：暂时独立                                                │
├──────────────────────────────────────────────────────────────┤
│ 右侧：选中理解详情                                             │
│ - 完整理解                                                    │
│ - 来源上下文                                                  │
│ - 所属领域                                                    │
│ - 局部关系：引用了谁 / 谁引用了它                              │
│ - 编辑 / 补来源 / 补关系                                      │
└──────────────────────────────────────────────────────────────┘
```

这不是最终视觉布局要求，而是信息架构方向：用户围绕“领域里的理解”工作，而不是在多个功能页之间切换。

---

## 4. 领域导航

### 4.1 目标

领域导航回答：

> 我现在要回到哪个领域的理解现场？

### 4.2 形态

左侧保留用户熟悉的领域 / Category 树。

它不是普通文件夹，而是用户回看个人理解的语境。

### 4.3 行为

- 用户选择一个领域后，中间区域展示该领域下的理解。
- 用户可以在当前领域中新建理解。
- 用户可以调整理解所属领域。
- 一个理解可以属于多个领域。

### 4.4 原则

不要把领域管理做成用户进入产品前必须处理的配置任务。领域应该服务于回看和沉淀，不应成为管理负担。

---

## 5. 理解卡片 / 条目流

### 5.1 目标

中间区域回答：

> 我在这个领域已经形成了哪些理解？

这是 Domain Workspace 的主体。它承接 value proposition 里的核心 moment：

> 原来我对这个领域的理解是这些。

### 5.2 每条理解最少展示

- 理解摘要：用户自己的判断、触动、困惑、教训或模型雏形。
- 来源摘要：它来自哪次经历、哪本书、哪段视频或哪次 AI 对话。
- 关系状态：连接了哪些已有理解，或暂时独立。
- 最近更新：帮助用户判断这条理解是否近期被修正过。

### 5.3 新建理解

用户在当前领域中新建理解时：

1. 系统在当前领域语境中创建一条新理解。
2. 用户直接写下自己的理解。
3. 来源和关系作为轻量补充，不打断写作。
4. 如果用户没有意识到关系，理解可以独立保存。

新建不应打开复杂表单或向导。

### 5.4 原则

理解卡片不是文章卡片，也不是资料卡片。它的核心是“我形成了什么理解”，来源和关系是支撑它的上下文。

---

## 6. 理解详情

### 6.1 目标

右侧详情回答三个问题：

1. 这条理解完整表达了什么？
2. 它从哪里长出来？
3. 它和哪些已有理解有关？

### 6.2 信息结构

```text
理解正文
  用户自己的完整表达

来源上下文
  - 来源类型：实践 / 书 / 视频 / 文章 / AI 对话 / 他人观点
  - 来源名称或场景
  - 触发原因：为什么它让我形成这个理解
  - 可选摘录 / 实践细节

领域归属
  - 当前领域
  - 其他关联领域

局部关系
  - 这条理解引用了谁
  - 谁引用了这条理解
  - 暂时独立状态
```

### 6.3 可执行动作

用户可以：

- 修改理解表达。
- 补充或修正来源。
- 调整领域归属。
- 搜索并连接已有理解。
- 移除或调整关系。
- 跳转到相关理解。

### 6.4 原则

详情不是只读页面，而是后续整理和修正的主要位置。

当用户回看时产生“这句话不准确”“这两个有关”“这个来源没写清楚”的感受，应能直接在详情里完成修正。

---

## 7. 局部关系面板

### 7.1 目标

局部关系面板回答：

> 这条理解在我的知识网里和哪些理解发生了显式关系？

### 7.2 形态

默认不显示全局大图，而是围绕当前选中理解展示局部关系：

- 它引用了哪些理解。
- 哪些理解引用了它。
- 它是否暂时独立。

### 7.3 行为

- 用户可以从局部关系跳到相关理解。
- 用户可以在回看时补关系。
- 用户可以移除不再成立的关系。
- 关系建立后，中间卡片和详情中都应可见。

### 7.4 原则

关系不是系统自动推断出来的结构，而是用户显式意识到的连接。

图谱可以帮助观察，但不能替用户创造知识网。

---

## 8. 图谱的位置

图谱不是主入口，而是 Domain Workspace 里的辅助观察模式。

### 8.1 图谱适合回答

- 当前领域里哪些理解已经连接。
- 哪些理解暂时独立。
- 某条理解在局部网络里的位置。
- 某些理解是否形成 cluster。

### 8.2 图谱不适合承担

- 作为日常写理解的入口。
- 作为来源上下文的主要表达方式。
- 替代领域内理解盘点。
- 自动生成关系。

### 8.3 MVP 判断

MVP 可以先不把图谱作为默认主视图。更合理的优先级是：

1. 领域内理解卡片 / 条目流。
2. 选中理解的来源和局部关系。
3. 需要观察结构时，再进入图谱辅助视图。

如果保留图谱，它必须：

- 只呈现用户显式关系。
- 允许孤岛存在。
- 点击节点能看到来源上下文。
- 不替代卡片 / 条目流。

---

## 9. 关键用户路径

### 9.1 沉淀新理解

```text
进入领域
  → 点击新建
  → 写下个人理解
  → 补来源
  → 可选连接已有理解
  → 保存
  → 这条理解出现在当前领域
```

关键点：

- 用户从领域语境开始，而不是从全局空白表单开始。
- 写理解是主动作。
- 来源和关系是轻量补充。
- 不强迫每条理解都建立关系。

### 9.2 回看领域

```text
进入领域
  → 浏览理解卡片 / 条目
  → 扫描来源和关系状态
  → 选中一条理解
  → 查看详情、来源和局部关系
```

关键点：

- 用户能获得领域盘点感。
- 来源和关系不能藏到很深。
- 独立理解也应如实出现。

### 9.3 后续整理

```text
进入领域
  → 发现旧理解需要修正
  → 打开详情
  → 修改表达 / 补来源 / 补关系
  → 保存
  → 当前领域的理解网络更新
```

关键点：

- 整理不是独立模块，而是发生在领域工作台里。
- 知识网随用户修正自然生长。

---

## 10. 不做成独立模块的东西

### Source 管理

来源不做一级模块。用户的目标不是管理来源库，而是让每个理解有根。

### Relation 管理

关系不做一级模块。关系是理解的一部分，应在写理解或回看整理时自然补充。

### AI 工作台

AI 不做 MVP 一级入口。PMF MVP 不是 AI 产品，AI 的正确位置是辅助用户已有理解。

### 全局图谱中心

全局图谱不做 MVP 主入口。它可以是观察模式，但不定义产品主路径。

---

## 11. 最小功能清单

### Domain Workspace 必须支持

- 选择领域。
- 查看当前领域下的理解。
- 新建理解。
- 编辑理解。
- 添加来源上下文。
- 选择或调整领域。
- 搜索并连接已有理解。
- 查看局部关系。
- 允许理解独立存在。
- 后续补来源、补关系、修正理解。

### 可以很轻

- 来源结构。
- 领域层级。
- 关系展示。
- 图谱视图。
- 搜索和筛选。

### 不做

- AI 自动提炼理解。
- AI 自动构建关系网。
- 强制关系填写。
- 复杂模板系统。
- 掌握度评分。
- 自动领域总结。

---

## 12. Product Shape 结论

PMF MVP 的产品形态应收敛为：

> 一个按领域组织的个人理解工作台。

它不是：

- 一个 AI 自动知识整理器。
- 一个图谱优先的关系可视化工具。
- 一个普通笔记 / 文件夹系统。
- 一个来源或关系管理后台。

它要让用户产生的感受是：

> 我进入某个领域，就能看到自己在这个领域里逐渐长出来的理解；每个理解都能追溯来源；有些理解已经连接成链条，有些暂时独立；我可以继续补充、修正、连接，让自己的知识网慢慢长出来。
