## 1. 业务背景

### 1.1 现状与问题

当前 Capture 页顶部的 `CaptureStats`（`modules/capture/dashboard/stats.ts`）只基于一种实体——「理解笔记（Understanding）」——统计总理解数、本周新增、连续记录天数、上下文总数，并配 12 周热力图。

它有三个与产品价值冲突的问题：

1. **统计对象单实体**：画布（Understanding Canvas）、对话（Agent 会话）等都是系统中的知识资产，统计却只看理解——"拿单实体统计范式服务多实体产品"（调研发现）。
2. **激励了错误的对象**：「连续记录」按"连续创建理解"计算、热力图按"创建数"着色——本质在激励**沉淀产出量**，与修订后的价值主张（激励参与、不激励产出）冲突。
3. **占用了产品主场景的注意力**：统计以数量墙形式钉在 Capture 页顶部，而用户实际使用最多的主场景是与 Agent 的对话；知识管理垂类共识是"统计低打扰、不占首页第一屏"。

### 1.2 为什么重做

用户对产品的核心使用是"和 Agent 对话"这一过程；对用户来说，最有价值的统计是**参与过程的数据**（对话、复盘、咀嚼、整理），而不只是"沉淀了多少资产"。行业中：电商/运营后台的"实时层 + 趋势层 + 可钻取"看板结构成熟可借鉴（Zonos/Shopify/Stripe）；个人知识工具的统计呈现"单实体 + 热力图 + 数字可回看"是共识下限；跨实体统一看板与"对话过程统计"仍属行业空白——本设计填补的正是这一空白，但每个构成元素都有成熟参照。

### 1.3 与价值主张的关系（2026-08-17 修订后）

- 可激励：**参与思考的过程**——对话、复盘、咀嚼、追问、回看整理。
- 不可激励：**沉淀产出的结果**——理解数、画布数、上下文数、字数、打卡产量。
- 不碰的红线：知识边界分数 / 抽象仪表盘（Never）、输入量 / 收藏量作为激励（Never）、AI 自动建关系并入库（Never）。

一句话：可以鼓励一个人思考得多，但不应该鼓励这个人产出很多内容。

## 2. 产品原则（不可走偏）

1. **只激励参与，不激励产出**：热力图 / 任何节奏可视化按"参与动作"着色；产出量只在资产块中性呈现，不带激励元素。
2. **数字必须可回看**：任何一个数字点击后都能落到底层内容（对话、理解、画布列表），拒绝"死数字"（垂类共识 4）。
3. **不做评价体系**：无分数、无评级、无排名、无 streak（第一版明确不做；streak 若未来引入必须严格按参与口径）。
4. **低打扰**：独立页 + 轻入口，不占首页第一屏、不干扰对话主场景。
5. **过程为主，资产为次**：页面上半是参与过程（主），下半是沉淀资产（次）；对话数据是过程块的核心。
6. **如实呈现**：资产块的"结构状态"（孤岛 / 缺上下文）是事实列表，不做评分、不替用户判断优劣。

## 4. 参与口径（过程块的核心定义）

"参与" = 一次有内容的思考动作。第一版口径：

| 动作                                 | 数据源                                                | 计入参与      |
| ------------------------------------ | ----------------------------------------------------- | ------------- |
| 开启 / 继续一次 Agent 对话（有消息） | Sessions 索引（`sessions-index.json`，消息数 > 0）    | ✅ 参与核心   |
| 创建理解 / 编辑理解正文（回看打磨）  | DB `understandings.created_at` / `updated_at`         | ✅            |
| 补充 Context                         | DB `contexts.created_at`                              | ✅            |
| 创建画布 / 画布新增元素或连线        | DB `canvas_elements` / `canvas_edges` 的 `created_at` | ✅            |
| 画布位置 / 尺寸微调                  | DB `updated_at`（噪音大）                             | ❌ 第一版不计 |
| 仅打开应用、纯浏览                   | 无记录                                                | ❌            |

边界说明：写一条理解本身包含思考（参与），但它同时是产出；本设计的原则是**参与口径决定"哪天算活跃"**，**产出量永不进入激励性展示**——所以"创建理解"计入参与热力图、但"理解总数"只在资产块中性出现。

## 5. 明确不做（版本边界）

- 第一版不做：streak（连续记录）、排名（社交比较）、评分 / 分数（如 RescueTime Pulse）、周期性汇总报告（Wrapped 式）、导出、目标设定。
- 不做跨实体数量的单一大数字（"总资产 N"这类抽象汇总不属于任一资产类型的可回看数字）。
- 画布位置微调不计入参与（待元素级变更检测能力成熟后再议）。

## 6. 技术路径概要

参考：`understanding-canvas-backend-implementation-plan.md` 的分期风格（本页沿用仓库现有分层，不引入新架构）。

1. **数据层**：新增主进程侧聚合服务（暂名 `InsightsService`，`apps/electron/src/main/services/`），一次性返回：
   - 过程数据：读 `sessions-index.json` 聚合按日对话参与（复用 `pi-session-log` 的索引读取）；
   - 资产数据：复用 understanding / canvas 的查询（理解 `createdAt/updatedAt`、chapter；画布 `createdAt`；元素 / 连线 `createdAt`）。
2. **统计纯函数**：`renderer` 侧沿用现有 `computeCaptureStats` 模式改造为多事件输入（`stats.ts` 迁移 + 重写测试；`stats.test.ts` 测试模型不变）。
3. **页面**：新 `renderer` 模块（暂名 `modules/insights/`）：页面骨架 + 热力图组件（复用现有 `CaptureStats` 的网格渲染，改为跨实体事件输入）+ 实时层 + 资产列表。
4. **迁移**：移除 Capture 页 `CaptureStats` 引用与相关测试；`AppNavRail` 增加导航项，`router` 增加路由。
5. **前置约定**：实现前阅读 `frontend-guide.md`；组件是否进入 Storybook 按 `storybook-principles.md` 判断；Feature / Acceptance 修改按 `test-case-principles.md`。

## 8. 待办 / 待定

- **页面命名**：工作名「参与回顾页」（路由 `/insights`）；候选：回顾（Recap）/ 足迹（Traces）/ 参与概况（Participation Overview）。定名后同步更新 rail 导航文案与路由。
- **会话数据颗粒度**：确认 sessions 索引能支撑"按日对话数 / 消息数"聚合的可用字段（与 `AgentSessionSummary` 对齐验证）。
- **结构状态的数据来源**：孤岛 = 未出现在任何画布的理解（反向 join `canvas_elements.understanding_id`，参考 M6-6 已有能力）；缺上下文 = `contexts` 无记录的 understanding。
- **接口形态**：一次性聚合 vs 按块查询，实现时按数据量决定（个人本地库规模下优先一次性聚合）。
