# UX Workflow

`docs/2-design/workflow` 放的是 UX 文档写作工作流。这里的重点不是把一份大模板从头填到尾，而是把 UX 判断拆成一组可以独立调用、又能组合成完整论证链的工作单元。

## 这个 workflow 的功能

UX workflow 用来把产品决策翻译成用户行为路径、界面状态、边界处理和体验验收条件。

它的产出发生在线框图之前，作用是让设计方案有明确依据：每个界面判断都能追溯到用户目标、范围和约束，而不是凭直觉补齐。

## 组合逻辑

五个核心单元不是并列清单，而是一条从「为什么设计」到「怎么验证」的推导链：

```
0. 文档定位与节间逻辑
        ↓ 定义 UX 文档的用途、读者和依赖关系
1. 用户是谁，他要做什么
        ↓ 给后续所有判断提供目标、范围和约束
2. 用户的行动路径
        ↓ 把目标翻译成空间结构和动态过程
3. 路径上每个节点的设计    4. 路径之外会发生什么
        ↓                      ↓
5. 怎么验证用户体验是对的
        ↓
6. 自检清单
```

核心依赖关系：

- 第 1 节定义目标、范围和约束，后续所有设计判断都必须能追溯到这里。
- 第 2 节定义用户能到哪里、怎么走，是第 3 节界面状态和第 4 节边界场景的来源。
- 第 3 节描述路径上的界面节点、组件和过渡意图。
- 第 4 节补齐路径之外的数据边界、操作边界和状态恢复。
- 第 5 节把第 1.1 的用户障碍转成可判断、可测试的体验验收条件。
- 第 6 节用于提交前检查，确保前后依赖没有断裂。

## 怎么用

先判断当前缺的是什么，再进入对应单元。

- 不确定 UX 文档该承担什么职责：看 [0-文档定位与节间逻辑.md]
- 不确定用户目标、设计范围或约束：看 [1-用户是谁他要做什么.md]
- 不确定用户怎么走、注意力在哪里：看 [2-用户的行动路径.md]
- 要细化界面状态、组件行为和过渡意图：看 [3-路径上每个节点的设计.md]
- 要覆盖异常、极端数据、撤销和恢复：看 [4-路径之外会发生什么.md]
- 要定义体验是否成立的判断方式：看 [5-怎么验证用户体验是对的.md]
- 提交 UX 文档前做完整检查：看 [6-自检清单.md]

## 使用原则

- 每个单元只解决当前层级的判断，不顺手替后续章节补内容。
- 上一节的输出，必须成为下一节的输入。
- 如果某个设计决策无法追溯到第 1 节，先回到目标、范围或约束重新判断。
- 如果第 3 节或第 4 节出现第 2 节没有承接的状态，先补路径，再补界面。
- 第 5 节的每条验收条件都要能追溯到第 1.1 的某个障碍。
