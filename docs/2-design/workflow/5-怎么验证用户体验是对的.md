## 5. 怎么验证用户体验是对的

### 5.1 每条用户目标对应的可操作验收条件

#### 存在原因

没有验收条件，「好不好」只能靠直觉判断。验收条件把设计目标变成可判断、可测试的具体标准，让设计师、PM 和 QA 在同一套标准下评估。

#### 验收条件的三个必须

每条验收条件必须满足：

1. **可判断**：能回答「是 / 否」，不能是「界面美观」这种主观描述
2. **可测试**：有明确的判断方式
3. **有来源**：能追溯到 1.1 的某个障碍

验收条件只能验证 UX 文档已经定义的体验目标和边界。不要为了“完整测试”而加入同步、冲突、撤销、失效、网络错误等产品并未定义的机制；如果这些能力需要验证，先回到第 1.3、2、3、4 节补足依据。

#### 判断方式类型

| 类型         | 说明                               |
| ------------ | ---------------------------------- |
| 操作步骤计数 | 计算完成任务所需的点击次数         |
| 界面量测     | 测量屏幕上元素的数量、位置、层级   |
| 操作回归验证 | 执行操作后观察状态变化是否符合预期 |
| 可用性测试   | 请用户执行任务并观察行为           |
| 功能测试     | 验证功能是否按业务规则运行         |
| 数据验证     | 检查数据是否正确更新               |
| 端到端测试   | 跨模块验证数据一致性               |

#### 应该写什么

- 按障碍分组（每个障碍一组，与 1.1 对应）
- 每组 3–6 条验收条件，覆盖正向场景和已定义的边界场景
- 最后单独一组「通用验收条件」，覆盖跨障碍的基础体验

#### 格式

按障碍分组，每组标题为「障碍 X：[障碍名]」，组内两列表格：`验收条件 | 判断方式`

#### 质量信号

✅ **好的写法**

- 每条条件是「可以回答是/否的问题」：

  > ✅ 「从点击新建到进入可输入状态不超过 2 步，全程无弹窗」
  > ❌ 「新建流程简洁」

- 体验验收 vs 功能验收：
  > ❌ 「能创建 Thought」（功能验收，不是体验验收）
  > ✅ 「从点击新建到光标就位不超过 2 步，且不经过任何弹窗或表单」

❌ **常见错误**

- 验收条件没有异常场景（只验证 happy path）
- 条件无法追溯到 1.1 的障碍（说明这个条件可能不必要）
- 判断方式是「视觉检查」（太模糊，不同人有不同判断标准）
- 验收条件验证了 UX 文档没有定义的技术机制
