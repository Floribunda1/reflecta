## 2. 用户的行动路径

### 2.1 用户能去的所有地方（信息架构）

#### 存在原因

在画任何具体界面之前，需要先定义「这个模块有哪些地方、用户可以在哪些地方之间移动」。信息架构是设计空间的地图，后续所有路径描述和界面设计都在这张地图上展开。

信息架构不是导航设计，不是功能列表，也不是流程图——它是**空间结构**。

#### 应该写什么

- 所有用户可以「到达并停留」的位置（包括状态，如「浏览态」和「详情态」是两个不同的位置）
- 各位置之间的层级关系（父子关系）
- 每个位置上的主要操作入口（可以去往哪里）

只写用户在这个模块里真实可能到达和停留的位置。不要因为通用产品模板而把 loading、error boundary、同步中、冲突处理、失效对象等技术状态默认塞进信息架构；除非它们已经是产品决策、技术约束，或者用户在真实路径中一定会感知到。

#### 格式

树形结构（用缩进表示层级）。每个节点是用户可以停留的地方，操作入口可以作为子节点，但要与「位置」节点有明显区分。

#### 质量信号

✅ **好的写法**

- 信息架构是空间结构，用户可以在树上找到自己「现在在哪」
- 把「浏览态」和「详情态」作为两个独立节点，因为用户的感知位置不同

❌ **常见错误**

- 信息架构变成功能列表（按功能名称平铺，而不是按用户空间感知组织）
- 把操作（如「删除」）和位置（如「详情态」）混在同一层级
- 把用户不会停留的技术过程写成位置（如把底层数据读取过程写成一个页面）

### 2.2 每条路径的完整过程

#### 存在原因

路径描述是 UX 文档的核心。它把信息架构从静态地图变成动态过程，逼迫设计师想清楚「用户在每一步到底在做什么、注意力在哪、系统应该做什么」。

**「注意力应在哪里」是这个文档最重要的一列。** 它直接驱动布局决策和信息层级判断：用户注意力在哪里，那里就应该是视觉主焦点；用户不需要注意的，就不应该争夺视线。

#### 应该写什么

每条 Journey 包含三个部分：

**① 用户处境**

一段话描述：用户是谁、此刻处于什么状态、带着什么目标进入这条路径。

**② 四列步骤表格**

| #   | 用户做了什么 | 这一步注意力应在哪里 | 系统响应 | 异常 |
| --- | ------------ | -------------------- | -------- | ---- |

各列说明：

- **用户做了什么**：从用户视角描述具体行为
  - ✅ 「用户扫视卡片列表，寻找有没有熟悉的判断」
  - ❌ 「用户滚动列表」（动作描述，没有目的）

- **注意力应在哪里**：用户的视觉焦点和认知焦点，以及**为什么**
  - ✅ 「卡片标题和 3 行 Preview——用户靠这两个元素唤起记忆，不需要看完整正文」
  - ❌ 「卡片区域」（太模糊，无法驱动布局判断）

- **系统响应**：系统给用户什么反馈，从用户感知描述，不是实现描述
  - ✅ 「右侧切换显示该 Category 下的列表；Category 路径更新至页面标题区」
  - ❌ 「调用 API 获取 Thought 数据」

- **异常**：这一步用户出错、放弃、系统失败时发生什么（每步都要想；确认无异常写「—」）

**③ 路径外异常汇总**

步骤表格结束后，单独列出「无法在单步中承接」的异常：

- 用户中途放弃（返回到哪里、状态如何恢复）
- 创建后立刻离开
- 操作被打断（来电话、切换 App）

异常只写当前产品语境下用户会实际遇到并感知的分支。比如 local-first 应用里，如果产品没有同步、冲突、失效、撤销机制，就不要在 Journey 里替工程假设这些状态；如果某个错误只属于底层实现失败，且 UX 不知道用户会看到什么，就不要写成界面路径。

#### Journey 数量

Journey 数量与 1.1 的障碍数量一一对应——每个障碍对应一条 Journey，验证这个障碍确实被某条路径解决了。

#### 质量信号

✅ **好的写法**

- 「注意力」列是认知焦点，不是 UI 元素名称
- 每条异常都说明了「用户会看到什么」和「上下文如何保留」
- 用户处境段落能让读者感受到用户当下的「热程度」和「时间压力」
- 异常来自用户行为或已知产品约束，不来自通用技术想象

❌ **常见错误**

- 「注意力」列留空或写「整个界面」（等于没有写）
- 异常只写「显示错误提示」（没有说状态如何保留）
- 步骤从系统视角描述：「系统判断用户是否已登录」而不是从用户视角
- 异常场景只想了「系统失败」，没有想「用户出错」和「用户主动放弃」
- 在没有产品或技术依据时，默认补上网络中断、同步冲突、失效对象、undo toast 等机制
