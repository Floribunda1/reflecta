# Reflecta PMF Feature Set

> 日期：2026-06-10
>
> 主题：基于 `value-proposition.md` 推导 PMF 阶段的 Feature Set。
>
> 方法：遵循 `feature-set-guide.md`，先从 Value Proposition 拆出目标用户、关键场景、核心痛点和关键收益，再列出用户完成目标必须经历的 Job，最后才把 Job 映射成产品能力。
>
> 重要约束：不要让现有 solution 概念反向定义 problem。`Thought`、`Context`、`Category`、`Connection` 是 Reflecta 当前产品里的对象，但在 Feature Set 推导的前半段，只能作为后续能力映射的候选承载物，不能用来替代用户语言。

---

## 1. 前置 Value Proposition

来自 `docs/1-product/value-proposition.md`：

> Reflecta 帮用户把学习、实践、观察和对话之后发生的有效思考，沉淀成有上下文、有边界、可回看的个人理解。长期回看某个领域时，用户能清楚看到自己对这个领域的理解是什么，以及这些理解分别从哪些经历、书籍、视频、实践和 AI 对话中长出来。

更短的表达：

> Reflecta 帮你把学习、实践和对话，沉淀成可追溯的个人理解。

这次 Feature Set 推导不以“做一个更强的笔记系统”为目标，而是验证这个 value proposition 是否能在一个足够小的产品闭环中成立。

---

## 2. 已确认的产品哲学

### 2.1 用户是大脑，AI 是辅助

Reflecta 的价值观不是“AI 帮用户自动整理知识”，而是：

> 用户完成理解和判断，AI 只提供信息、建议、追问、对比和候选表达。

这意味着 PMF 阶段不能把“AI 自动总结用户输入材料并生成知识条目”当作核心能力。那种形态看起来高效，但会绕过用户自己的理解过程。

用户手动表达自己的理解，不是低效录入，而是整理和内化的一部分。用户在把一个模糊触动写成自己的语言时，才更可能让这个理解真的进入自己的认知结构。

### 2.2 AI 的正确位置

AI 可以辅助，但不能替代用户形成理解。

允许的 AI 辅助包括：

- 用户已经有一个模糊判断，AI 帮他追问边界。
- 用户理解了一个意思，但表达不够 precise，AI 提供候选表述。
- 用户想补充来源上下文，AI 提醒哪些场景、材料片段或对话内容值得保留。
- 用户复盘实践时，AI 提供问题框架，帮助用户自己看见假设、结果和教训。
- 用户回看旧理解时，AI 提供对比、相似概念、场景例子或外部信息作为思考催化剂。

不应作为 PMF Core 的 AI 能力：

- 用户丢一段原始材料，AI 自动批量总结出“你应该记录的理解”。
- AI 自动构建完整知识体系。
- AI 替用户判断哪些内容值得沉淀。
- AI 生成大量看似完整、但用户没有真正理解和确认的内容。

---

## 3. PMF Feature Set 的主验证场景

我们当前选择的主验证场景是：

> 用户在一次学习、实践或对话之后，已经意识到其中有一个值得留下的个人理解。Reflecta 帮助用户用自己的语言把这个理解沉淀下来，并保留它从哪里长出来。之后，当用户回看某个领域时，能感受到这些理解正在聚沙成塔。

这意味着 PMF 主验证不押在“AI 帮用户从原始材料里提炼观点”，而押在：

- 用户愿不愿意主动沉淀自己的理解。
- 沉淀时，用户是否愿意保留来源上下文。
- 回看时，用户是否能感受到“我对这个领域的理解是这些，它们来自这些经历和材料”。

---

## 4. 用用户语言描述的核心链路

这一节刻意不使用 `Thought` / `Context` / `Category` 这些现有产品对象。

### 主 Job：把一次有效思考沉淀下来

1. 用户经历了一次学习、实践、观察或对话。

   例子：看完一段视频、读完一本书中的一章、完成一次项目实践、经历一次交易亏损、和 AI 深聊一次产品问题。

2. 用户意识到其中有一个值得留下的个人理解。

   这个理解可能是判断、触动、困惑、教训、模型雏形，也可能只是“我好像意识到这里有个重要区别”。

3. 用户需要用自己的语言表达这个理解。

   这里的关键不是生成漂亮文本，而是把模糊理解转成自己的表达。表达过程本身就是整理过程。

4. 用户需要保留这个理解从哪里来。

   用户未来回看时，不只是看到一句抽象结论，而是能知道：

   - 它来自哪次经历、哪本书、哪段视频、哪场 AI 对话。
   - 当时发生了什么。
   - 为什么这件事触发了自己。
   - 这个理解在什么具体场景中成立。

5. 用户需要把这个理解放到一个以后能回看的领域语境里。

   用户不是只想把内容丢进时间流，而是希望以后回到“交易心理”“AI / Agent”“产品设计”“认知哲学”等领域时，能看到自己已经形成过哪些理解。

### 最小回看 Job：确认这些理解正在聚沙成塔

6. 用户之后回看某个领域。

   用户想看到的不是资料库，不是时间线，也不是抽象指标，而是：

   - 我在这个领域已经有哪些理解。
   - 每个理解分别来自哪些经历、材料或对话。
   - 哪些理解有丰富来源支撑。
   - 哪些理解还只是一次触动，尚未被充分咀嚼、验证或连接。
   - 我的理解边界在哪里。

---

## 5. 关于“关系”的当前共识

关系不是一个额外的整理任务，而是理解本身的一部分。

当用户意识到两个理解之间有关系时，这个“意识到关系”的瞬间本身就是一次有效思考。它可能发生在不同 timing：

- 用户在看到一个新材料时，敏锐地意识到它和某个已有理解有关，而且处在同一条链条的不同环节。
- 用户在写下新感悟时，自然而然地引用或连接到已有理解。
- 用户当下没有意识到任何关系，新理解先独立存在。
- 用户后续回看整理时，突然意识到“原来这两个是同一个东西”“原来它们是上下游”“原来它们属于同一个模型”，于是补关系、修正知识。

因此，PMF Core 里的“知识网”不应该是系统自动推断出来的网，而应该是用户显式表达出来的理解关系，产品负责如实记录和呈现。

这带来几个设计原则：

- 关系应该能在用户表达理解的过程中自然发生，而不是被强制成每次沉淀都必须填写的关系表单。
- 关系也应该能在后续回看、整理、修正知识时补充。
- 没有关系的理解可以先独立存在。
- 孤岛不是错误。孤岛只是“尚未被整合的理解”。
- AI 可以后续建议可能关系，但不能把自动推断关系直接当作用户的知识网。

所以当前对关系能力的 problem / job 层描述是：

| 用户状态 | 用户 Job |
| --- | --- |
| 写一个新理解时意识到它和已有理解有关 | 在表达过程中自然连接已有理解 |
| 回看整理时发现两个理解其实有关 | 补充、修正或重组已有关系 |
| 当下没有意识到关系 | 允许理解先作为独立积累存在 |
| 回看某个领域 | 如实看见已经显式建立的关系，以及尚未连接的独立理解 |

---

## 6. 离散增强 Job

这些 Job 不属于每次沉淀都必须发生的连续链路，但它们能提升沉淀质量，后续会进入 Core / Support / Delight 的筛选。

### 6.1 把已有理解表达得更 precise

用户已经理解了一个意思，但表达不够准确，或者用了很大的词。

用户需要：

- 区分相近概念。
- 找到更准确的表述。
- 看见表达里的含混词。
- 确认这句话到底想表达哪个核心命题。

AI 可以在这里提供候选表述，但用户必须选择、修改和确认。

### 6.2 让来源上下文更丰富

用户已经写下了一个理解，但来源上下文太薄。

用户需要被提醒：

- 当时是什么具体场景。
- 哪个材料片段触发了自己。
- 这个理解和自己的哪次实践有关。
- 为什么当时觉得它重要。

这里的目标不是把来源变成 metadata，而是帮助用户未来能回到现场。

### 6.3 回看时发现还没想透的地方

用户回到某个领域时，不只是想看已有理解，也想知道哪里还薄。

可能的薄弱表现：

- 某个理解只有一句抽象结论，没有来源上下文。
- 某个理解来自单一材料，还没有和自己的实践发生关系。
- 某个领域里有很多零散理解，但没有形成更高层结构。
- 两个理解看起来相关，但用户说不清它们是什么关系。

这些薄弱点可以成为下一次有效思考的入口。

---

## 7. 当前暂不进入 solution 映射

到这里为止，本文只确认了 problem / job 层判断。

下一步才会把这些 Job 映射为产品能力，再进一步判断哪些能力属于：

- Core Feature：没有它，value proposition 不成立。
- Support Feature：不直接创造核心价值，但支撑核心链路稳定使用。
- Delight Feature：提升体验，但不是 PMF 验证必需。
- Not Now：看起来有用，但会扩大边界或违背产品哲学。

后续映射时可以考虑现有对象如何承载这些能力，但必须保持一个原则：

> 先从用户要完成的 Job 出发，再决定产品对象和功能形态；不要因为已有 `Thought` / `Context` / `Category`，就反过来把用户问题写成“用户需要创建 Thought / 填写 Context / 选择 Category”。

## 8. Job 到产品能力的当前映射

本节开始从 Job 进入产品能力，但仍不讨论 UI 形态，也不讨论现有对象如何承载。

| 用户 Job | 用户现在的痛苦 | 需要的产品能力 |
| --- | --- | --- |
| 用自己的语言表达一个理解 | 想法停留在脑子里，或散落在聊天、备忘录、材料旁边 | 低摩擦表达个人理解 |
| 保留这个理解从哪里来 | 以后只剩一句抽象结论，不知道它来自哪次经历、哪本书、哪段视频或哪次 AI 对话 | 来源上下文记录能力 |
| 把理解放入以后能回看的领域语境 | 内容按时间散落，之后无法按“我对这个领域理解了什么”来回看 | 领域语境组织能力 |
| 在意识到关系时连接已有理解 | “这个和之前那个有关”的瞬间没有被沉淀，之后关系又丢失 | 用户主导的关系表达能力 |
| 允许暂时没有关系的理解独立存在 | 如果产品强迫整理关系，会打断沉淀过程，也会制造负担 | 独立理解沉淀能力 |
| 后续回看时补充、修正关系 | 用户后来才意识到“原来这两个是同一个东西 / 上下游 / 同一模型” | 后续整理和修正能力 |
| 回看某个领域已有理解 | 不知道自己在这个领域到底已经理解了什么 | 领域内理解盘点能力 |
| 看见理解、来源、显式关系构成的结构 | 知识散成条目，看不到自己已经形成的理解网络 | 个人理解网络呈现能力 |

## 9. 当前 Core 能力判断

当前判断：下面这些能力都是 PMF Core。

1. 低摩擦表达个人理解
2. 来源上下文记录能力
3. 领域语境组织能力
4. 用户主导的关系表达能力
5. 独立理解沉淀能力
6. 后续整理和修正能力
7. 领域内理解盘点能力
8. 个人理解网络呈现能力

它们看起来有 8 项，但不应理解为 8 个大型功能模块，而是同一个最小闭环里的必要能力：

> 用户亲自沉淀理解、保留来源、归入领域语境、在意识到关系时连接已有理解；产品允许理解先独立存在，也允许后续补充和修正关系；当用户回看某个领域时，产品如实呈现这些理解、来源和显式关系构成的个人知识网。

### 9.1 为什么“后续整理和修正能力”是 Core

很多关系并不是在第一次沉淀时就出现的。

用户可能先记录一个独立理解。几天、几周甚至几个月后，用户在回看某个领域时，才突然意识到：

- 原来这两个理解是在说同一个东西。
- 原来一个理解是另一个理解的上游或下游。
- 原来两个看似不同的经历，共享同一个心智模型。
- 原来过去某个理解需要被修正，因为新的经历改变了它的边界。

如果产品只能支持“当下记录”，但不能支持后续补关系、修正理解和重组知识，那么它无法支撑“知识网自然生长”。因此，后续整理和修正不是增强体验，而是 PMF Core。

## 10. 已达成共识的 PMF MVP Feature Set

这一版 Feature Set 只围绕一个最小闭环：

> 沉淀个人理解 → 保留来源 → 放入领域 → 显式连接关系 → 后续修正 → 回看知识网

它要验证的不是“Reflecta 能不能做很多知识管理功能”，而是：

> 用户能否把一次学习、实践或对话后的有效思考，沉淀成可追溯的个人理解；长期回看时，能否如实看到自己在某个领域里的理解、来源和显式关系。

### 10.1 Core Features

| Feature | 对应 Job | 为什么是 Core |
| --- | --- | --- |
| 个人理解记录 | 用户用自己的语言写下一个理解 | 没有它，产品无法承载“个人理解” |
| 来源上下文记录 | 用户保留这个理解从哪里来 | 没有它，理解会退化成抽象结论 |
| 领域归属 | 用户把理解放进以后能回看的领域语境 | 没有它，长期回看无法形成“我对这个领域理解了什么” |
| 用户显式关系表达 | 用户在意识到关系时连接已有理解 | 没有它，知识网无法由用户理解自然长出来 |
| 独立理解保留 | 用户暂时没意识到关系时，理解也能独立存在 | 没有它，产品会强迫整理，违背自然积累 |
| 后续修正与补关系 | 用户回看后能修改理解、补充来源、补关系 | 没有它，知识网不能自然生长 |
| 领域内回看 | 用户能回到某个领域，看已有理解 | 没有它，无法验证“聚沙成塔” |
| 个人知识网呈现 | 用户能看到理解、来源、显式关系构成的结构 | 没有它，只是记录工具，不是 Reflecta |

### 10.2 Support Features

Support Features 只保留 Core 跑起来真正需要的支撑项，不展开成宽泛产品能力。

| Feature | 支撑什么 |
| --- | --- |
| 查找已有理解 | 支撑用户在表达关系时找到要连接的已有理解 |
| 基础编辑入口 | 支撑后续修正、补来源、补关系 |
| 基础浏览 / 过滤领域内容 | 支撑领域内回看 |
| 持久保存与可靠数据结构 | 支撑长期积累，不创造核心认知价值但必须稳定 |

### 10.3 PMF Later

`Later` 只记录“可能属于 Reflecta 方向，但不进入 PMF MVP”的能力。它不是无限枚举的“不做列表”。

| Later | 原因 |
| --- | --- |
| AI 辅助澄清表达 | 贴近 value proposition，但手动沉淀和回看闭环要先成立 |
| AI 提醒补充来源上下文 | 有助于提高沉淀质量，但 PMF 先验证用户是否愿意主动保留来源 |
| AI 建议可能关系 | 有助于发现连接，但必须建立在用户主导关系之后 |
| 自动识别薄弱理解 | 重要的下一阶段能力，但 MVP 先做到如实呈现知识网 |
| 心智模型聚合 / 领域结构洞察 | 贴近长期愿景，但需要足够沉淀数据作为基础 |

### 10.4 Non-goals / Never

`Never` 只记录会破坏 Reflecta 产品哲学的方向，不做无穷列举。

| Never | 原因 |
| --- | --- |
| AI 替用户自动生成“个人理解”并直接入库 | 违背“用户是大脑，AI 是辅助”；绕过用户自己的理解和表达过程 |
| AI 自动构建关系网并直接当作用户知识网 | 关系必须来自用户显式理解；AI 推断最多只能作为建议 |
| 用输入量、打卡、收藏量作为核心激励 | 会鼓励无效积累，偏离“有效思考沉淀” |

### 10.5 最小验收标准

这版 Feature Set 成立时，用户应该能完成：

1. 我刚刚形成了一个理解，能用自己的语言写下来。
2. 我能记录它来自哪次学习、实践或对话，以及为什么触发我。
3. 我能把它放进某个领域。
4. 如果它和已有理解有关，我能自然连接。
5. 如果暂时没有关系，它也能独立存在。
6. 几天后我回看这个领域，能看到已有理解、它们的来源、以及我显式建立过的关系。
7. 我能修正旧理解、补来源、补关系。

### 10.6 当前判断

MVP 不是 AI 产品，也不是图谱产品，而是：

> 一个能让个人理解带着来源和关系长期生长的最小系统。

AI 和图谱都可能成为后续很重要的产品形态或增强能力，但在 PMF Feature Set 层，它们不是定义问题的起点。当前最小系统首先要证明：用户愿意亲自沉淀理解、保留来源、表达关系，并在回看时感受到自己的知识网正在如实生长。
