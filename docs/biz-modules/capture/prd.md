# Capture 模块设计文档

> 分类：模块设计契约
>
> 适用范围：Reflecta 高频内容工作台的用户任务、体验策略、信息架构、UX 结构、journey validation、detail design 与实现 review。
>
> 版本：v2.0
> 日期：2026-04-27

Capture 是 Reflecta 的高频内容工作台。它服务用户在认知事件发生时的完整闭环——快速把想法归入正确语境，在已有语境中快速回忆知识，并在打开单条 Thought 后用轻量背景信息补足理解。Capture 不是完整写作室，也不是内容管理后台，而是让用户在"记录→回忆→理解"之间保持低摩擦循环的现场。

本模块按 [Product Workflow](../1-product/workflow/) 的核心模块形态拆分。所有实现判断必须能追溯到阶段文档，不能只凭局部样式偏好调整。

---

## 模块定位

| 项              | 判断                                                                  |
| --------------- | --------------------------------------------------------------------- |
| 模块类型        | 高频核心工作台                                                        |
| 页面骨架        | `Navigation + Main Content`                                           |
| Primary Focus   | 右侧单一内容区（Thought 浏览态 / Thought 详情态）                     |
| Secondary Areas | 左侧分类导航、详情态整理延伸区                                        |
| 核心状态        | Thought 浏览态、Thought 详情态                                        |
| 设计边界        | Capture 负责写作和整理，关系探索交给 Contemplate，认知深化交给 Deepen |

## 1. 用户意图

### 意图一：新想法出现时，立刻把它放进正确语境，不打断当前节奏

- **用户处境**：用户刚看完一段视频、踩过一个坑、或工作中突然闪过一个判断，需要立刻记下来
- **想要结果**：这个想法被记录在一个明确的 category 下，之后能靠 category 快速找回，而不是散落成无法定位的碎片

**Case**：

> 用户在看一个关于"行为设计"的视频时，突然意识到"环境提示比意志力更可靠"——这是一个和自己过去经验高度共鸣的判断。用户立刻打开 Reflecta，左侧 Category 树已经选中"行为设计"，点击「+ Idea」后直接输入这条判断的核心内容，保存后新 Thought 立刻出现在列表中。整个过程不超过 30 秒，用户没有被打断看视频的节奏，也确信这个想法之后能通过"行为设计"这个 category 快速找回。如果当时要先选分类、填表单、再进编辑器，这个想法很可能就因为流程太长而被放弃记录了。

### 意图二：回到某个领域时，快速想起自己已经知道什么

- **用户处境**：用户隔了一段时间回到"交易心理"或"行为设计"这个主题，需要重新进入当时的思考语境
- **想要结果**：扫一眼就能唤起记忆，不需要重新精读每篇笔记，就能知道自己在这个领域已经积累了什么观点、经验和判断

**Case**：

> 用户两周前在"交易心理"Category 下记录了若干 Thoughts，今天想回到这个主题继续思考。用户选中"交易心理"，右侧出现 12 张 Thought 卡片。每张卡片显示标题、3 行正文 Preview、Idea/Insight 类型标签、Context 数量和双向链接数量。用户扫一眼就能想起："恐惧与贪婪的边界"是上次看访谈记录的，"止损即承认错误"是那次爆仓后的复盘，"仓位管理的核心是活下去"是一个 Insight，正文中引用了 3 条 Idea。用户不需要逐条打开精读，靠卡片上的线索就能在 1 分钟内重新进入当时的思考语境，并决定今天从"止损即承认错误"这条继续深挖。

### 意图三：看到一条旧笔记时，快速理解它从哪来、在什么背景下成立

- **用户处境**：用户打开了一条半年前记录的 Thought，记得自己写过，但记不清当时的具体情境、来源或证据
- **想要结果**：能在几秒钟内扫到来源、关键背景或相关经历，补足理解，决定是否需要更新或延伸

**Case**：

> 用户打开半年前记录的 Thought"重复会重塑大脑"，记得这是一个重要判断，但忘了当时是基于什么写的。用户点开详情，右侧 Context 列表显示两条背景：一条来自某本书的读书笔记（显示书名和核心摘录），一条来自一次晨跑时的个人观察（显示当时的具体情境和感受）。用户在 10 秒内就补足了理解——原来这个判断不是空想，既有外部理论支撑，又有个人经验印证。用户随即决定为这个 Thought 补充一条新的 Context：上周坚持早起一周后注意力确实提升了，进一步验证了这个判断。如果没有 Context，用户可能会误以为这是一条无根的口号，甚至考虑删除它。

### 自检

- "我刚才有个想法，得赶紧记下来，别让它跑了" → 会
- "让我看看我在这个领域已经积累了什么" → 会
- "这条笔记我当时是基于什么写的？" → 会

✅ 通过检验。

## 2. User Journey

### Journey 1：在某个 Category 下快速创建 Thought

**用户处境**

- 用户刚从外部信息中获得新想法，或刚踩过一个坑想记录经验
- 用户知道这个想法大致属于哪个 category，或者需要先选一个临时归属
- 用户当前处于"热状态"，记录窗口很短，不能被复杂流程打断

**任务路径**

- 用户进入 Capture，左侧 Category 树确认当前语境
- 用户点击新建入口，系统创建 Thought 并默认归属当前 category
- 用户直接在详情态输入标题和核心内容，不需要先填表单再进编辑器
- 用户保存后回到当前 category，新 Thought 立刻出现在列表中，可被快速找回

**成功标准**

- 用户不需要先进入复杂管理流程，就能把新想法落到正确语境
- 创建过程足够短，不打断外部阅读、工作或复盘节奏
- 新 Thought 创建后能被当前 category 立即承接，之后可以被快速找回

---

### Journey 2：快速浏览 Category 下的 Thoughts 并回忆知识

**用户处境**

- 用户已经在某个 category 下积累了一组 Thoughts
- 用户想快速回忆这个领域下已经形成的知识，不是来管理对象
- 用户通常靠标题、类型和少量线索就能唤起记忆，不需要逐条精读

**任务路径**

- 用户在 Category 树中选择要回忆的 category
- 右侧显示该 category 下的 Thought 卡片列表
- 用户扫描卡片上的标题、摘要、类型标签、Context 线索和少量 meta 信息
- 必要时使用搜索、筛选或子分类范围调整来缩小范围
- 用户点击某条 Thought 查看详情，看完后关闭返回，原 category 和浏览位置仍然保留

**成功标准**

- 用户能快速判断自己处在哪个 category 语境
- 用户能以合适密度浏览多个 Thoughts，靠少量信息完成回忆
- 用户打开和关闭 Thought 细节后，原 category、筛选和浏览位置仍然存在

---

### Journey 3：阅读 Thought 正文后快速扫描 Context

**用户处境**

- 用户已经从 category 下打开一条 Thought，正在阅读正文
- 用户需要快速确认这条 Thought 来自哪里、当时的背景是什么、有哪些补充材料
- 用户当前目标是理解和回忆，不是进入系统化整理流程

**任务路径**

- 用户阅读 Thought 的标题和正文
- 用户在右侧或下方并列区域扫描与该 Thought 相关的 Context 列表
- 每条 Context 显示内容摘要、来源类型和记录时间，可展开查看完整内容
- 用户根据 Context 快速补足来源、证据或背景理解
- 用户回到正文继续阅读，或返回 category 继续浏览其他 Thoughts

**成功标准**

- Context 与当前 Thought 的关系清楚，不需要用户重新判断归属
- 用户能快速扫过 Context 摘要或关键信息，不被迫进入编辑或管理流程
- Context 不压过正文，用户仍然感觉自己停留在当前 Thought 的理解过程里

## 3. 解法空间

### 卡点 1：新想法出现时，记录流程太长导致用户放弃捕捉

**参照 A：传统笔记应用（如 Evernote、Notion）**

- 介入位置：提供丰富的编辑器，支持复杂排版和模板
- 解决部分：记录内容格式完整，适合长文写作
- 局限 / 代价：打开和创建流程重，用户需要先选笔记本/页面、选模板、等待编辑器加载，热状态下容易放弃记录

**参照 B：速记工具（如 Apple Notes、Flomo）**

- 介入位置：极简输入框，一键记录
- 解决部分：记录门槛极低，新想法能被快速捕获
- 局限 / 代价：缺乏明确的分类语境，记录变成时间流，之后难以按主题找回；没有与已有知识的关联能力

**参照 C：语音/快捷指令捕捉**

- 介入位置：通过语音、小组件或快捷指令快速录入
- 解决部分：在移动场景下记录门槛最低
- 局限 / 代价：录入后仍需后续整理和分类；桌面场景下用户更倾向键盘输入；无法就地关联已有知识

---

### 卡点 2：笔记积累多了之后，回顾时信息过载，难以快速唤起记忆

**参照 A：文件夹/标签系统**

- 介入位置：通过层级文件夹或标签对笔记进行组织
- 解决部分：提供了分类维度，降低单列表信息密度
- 局限 / 代价：用户需要主动维护分类体系；分类和笔记是分离管理，回顾时需要先选分类再浏览；无法直观看到笔记之间的关系

**参照 B：时间线/信息流**

- 介入位置：按时间倒序展示所有笔记
- 解决部分：最近的内容最容易找到
- 局限 / 代价：旧内容快速沉没；用户需要靠记忆推断"那篇笔记大概是什么时候写的"；不适合按主题回忆

**参照 C：全文搜索**

- 介入位置：用户输入关键词，系统返回匹配结果
- 解决部分：在知道关键词时找回效率最高
- 局限 / 代价：用户需要先想起关键词；搜索结果缺乏语境，难以判断哪条才是要找的；不支持"我想看看这个领域我都有什么"的浏览式回忆

---

### 卡点 3：打开旧笔记后，不理解当时的背景、来源和证据

**参照 A：纯 Markdown 编辑器**

- 介入位置：正文即全部，来源和背景也写在正文里
- 解决部分：所有信息在一处，阅读连续
- 局限 / 代价：来源和正文混在一起，干扰核心观点阅读；无法结构化地管理多条来源；修改正文时容易破坏来源信息

**参照 B：独立附件/引用系统**

- 介入位置：笔记链接到外部文件、链接或数据库
- 解决部分：来源信息可以独立于正文管理
- 局限 / 代价：链接可能失效；外部资源与笔记内容脱节；用户需要跳转到外部查看来源，打断阅读节奏

**参照 C：双向链接笔记**

- 介入位置：通过在正文中使用 `[[title#id]]` 引用其他笔记，系统自动维护双向关联
- 解决部分：关系随写作自然产生，不需要离开编辑上下文去手动管理；被引用的笔记自动获得 backlinks，形成自然的知识网络
- 局限 / 代价：链接是关系层面的，不是背景层面的，无法回答"这条笔记是从哪来、基于什么经历写的"；Obsidian 等工具的双链缺乏结构化关联类型，仅表示"相关"

## 4. 产品决策

### 决策 1：Category 树作为左侧常驻导航，不是独立管理页面

**用户卡在**：用户需要快速确认自己处在哪个语境，以及新想法该归到哪。

**见过的解法**：

- 方案 A（独立分类管理页）：用户先到管理页维护分类，再回到工作台创建内容
- 方案 B（标签云/多选标签）：用户给 Thought 打多个标签，没有明确的层级语境
- 方案 C（时间流无分类）：所有内容按时间排列，用户靠搜索和记忆找回

**我们选择**：左侧常驻 Category 树，用户选中 category 后右侧立即显示该语境下的 Thought 列表。

**理由**：

- category 树让用户一眼看到自己有哪些领域，快速定位到目标语境
- 新建 Thought 自动继承当前选中的 category，减少归属决策成本
- 树形结构支持领域细分（如 `Finance > Trading > ICT`），契合多线学习者的知识结构

**放弃**：

- 放弃"独立分类管理页面"，因为那会让"维护分类"变成用户记录前的必经流程，打断热状态
- 放弃"纯标签系统"，因为标签缺乏层级语境，用户难以判断"我在交易领域的笔记"有哪些
- 放弃"纯时间流"，因为时间流不适合按主题回忆，旧内容快速沉没

---

### 决策 2：Thought 卡片列表承载浏览与回忆，不是缩小版详情页

**用户卡在**：用户想快速扫一眼就能唤起记忆，不需要逐条精读。

**见过的解法**：

- 方案 A（长列表展示完整正文）：用户在列表中就能看到全部内容
- 方案 B（极简标题列表）：只显示标题，信息密度过低
- 方案 C（数据表格）：行列展示 meta 信息，阅读负担重

**我们选择**：卡片式布局，每张卡片展示正文 Preview（3 行折叠）、类型标签、所属 Category、Context 数量、双向链接数量、创建/修改时间。

**理由**：

- 标题 + 3 行 Preview 足够唤起记忆，又不至于信息过载
- 类型标签（Idea / Insight）和 Context / 双向链接数量提供快速线索
- 卡片密度适合中等数量的 Thoughts 快速扫描

**放弃**：

- 放弃"列表展示完整正文"，因为那会让列表变成阅读区，降低扫描效率
- 放弃"仅标题列表"，因为缺乏类型和线索信息，用户无法快速判断这条 Thought 是什么性质
- 放弃"把卡片做成缩小版详情页"，因为那会混淆浏览态和详情态的边界

---

### 决策 3：详情态左右分栏，正文为主、Context 为辅，不是上下堆叠

**用户卡在**：用户阅读正文时需要同时参考来源和背景，上下滚动切换效率低。

**见过的解法**：

- 方案 A（正文和 Context 上下排列）：Context 放在正文下方
- 方案 B（Context 作为独立标签页）：用户需要切换 tab 才能看到 Context
- 方案 C（Context 和正文混排）：来源信息直接插入正文

**我们选择**：详情态左右分栏，左侧正文编辑区为主，右侧 Context 列表为辅；双向链接作为整理延伸区，不争夺第一视线。

**理由**：

- 左右并列让用户阅读正文的同时扫到 Context，不需要来回滚动或切换
- Context 作为独立对象管理，不与正文混排，保持正文纯净
- 双向链接虽然重要，但属于关系整理，不是每次打开 Thought 的首要任务，退到延伸位置

**放弃**：

- 放弃"Context 在正文下方"，因为展开 Context 时用户会失去正文参照，上下滚动打断阅读
- 放弃"Context 作为独立标签页"，因为那会隐藏来源信息，用户需要主动切换才能看到
- 放弃"Context 和正文混排"，因为那会干扰核心观点的阅读，且无法结构化地管理多条来源

---

### 决策 4：新建 Thought 直接进入详情态，不是先填表单

**用户卡在**：热状态下用户需要最短的创建路径，减少中间步骤。

**见过的解法**：

- 方案 A（弹窗表单）：用户先填标题、选分类、选类型，保存后再进编辑器
- 方案 B（独立创建页）：用户跳转到一个专门的创建页面
- 方案 C（内联快速输入）：在当前列表底部直接出现一个输入框

**我们选择**：点击新建后直接创建 Thought 并进入详情态，默认继承当前 category。

**理由**：

- 用户进入详情态后立刻可以写标题和正文，与后续编辑的体验一致
- 不需要先填分类（已自动继承）、不需要先选类型（默认 Idea，可后续改）
- 减少了一次"创建→打开"的切换，保护热状态

**放弃**：

- 放弃"弹窗表单"，因为弹窗增加了填写步骤，且表单与编辑器体验割裂
- 放弃"独立创建页"，因为跳转会打断当前 category 的语境感知
- 放弃"内联快速输入"，因为内联空间不足以承载可能需要补充的 Context 和关联操作，且创建后仍需要展开编辑

## 5. 版本边界

**目标**：

让用户在认知事件发生时，能在最短时间内把想法放进正确语境，在已有语境中快速回忆知识，并在打开 Thought 后快速补足来源和背景理解。

**非目标**：

- 不把 Capture 设计成长时间写作工作台（如长文撰写、Markdown 精排）
- 不在 Capture 中展开图谱探索和关系网络审视（交给 Contemplate）
- 不在 Capture 中做 AI 认知深化对话（交给 Deepen）
- 不把分类维护做成完整管理后台
- 不把 Context / 双向链接做成与 Thought 正文并列的系统整理中心

**MVP 边界**：

- **P0**：
  - Category 树：展示、选中、新建、重命名、删除、拖拽调整层级
  - Thought 卡片列表：按 category 展示、搜索、类型筛选、子分类范围切换、排序
  - Thought 详情态：正文编辑（Markdown）、Category 归属修改
  - Context 列表：展示、新增、编辑、删除
  - 双向链接：在正文中通过 `[[title#id]]` 引用其他 Thought，系统自动解析并维护关联；展示当前 Thought 引用了谁、被谁引用
  - 新建 Idea / Insight：从当前 category 直接进入详情态创建

- **P1**：
  - 卡片操作：删除 Thought、修改类型、在 Contemplate 中查看
  - 未分类筛选：快速找到没有 category 归属的 Thoughts
  - Thought 正文预览优化：超出 3 行折叠，点击展开

- **P2**：
  - 专注模式：隐藏侧边栏，延长写作停留
  - 批量操作：批量修改 category、批量删除
  - 导入导出：支持外部文件批量导入

## 6. 功能设计

### 模块：Category 树

**核心功能**：

- 左侧常驻展示树形分类结构，根节点为「All」
- 每个节点显示 Category 名称及其下的 Thought 总数（默认直属，可切换含子节点）
- 支持展开 / 折叠子节点、当前选中节点高亮
- 支持新建 Category（指定父节点）、重命名、删除（Thought 归入父节点，需二次确认）、拖拽调整层级

**关键业务规则**：

- 删除 Category 时，其下 Thought 必须明确归入父节点，不得直接删除 Thought
- 拖拽调整层级后，Thought 的 category 归属自动跟随新结构，不需要用户手动重新分配
- Category 树不是管理后台，维护操作通过右键菜单或轻量入口完成，不升级为主工作区

---

### 模块：Thought 浏览

**核心功能**：

- 按当前选中的 Category 展示 Thought 卡片列表
- 支持全文搜索当前 Category 下的 Thought 正文及 Context 内容，实时高亮匹配关键词
- 支持类型筛选（All / Idea / Insight）、子分类范围切换（仅当前 / 含后代）、排序（最新创建 / 最近修改）
- 卡片展示：正文 Preview（3 行折叠）、类型标签、所属 Category（面包屑）、Context 数量、双向链接数量、创建/修改时间

**关键业务规则**：

- 搜索和筛选结果必须保留当前 Category 语境，用户清除搜索后回到原 Category 状态
- Thought 卡片不是缩小版详情页，不承载正文编辑、Context 完整内容或关系图谱
- 卡片上的双向链接数量可点击，点击后跳转至 Contemplate 并高亮该节点，不在 Capture 中展开图谱

---

### 模块：Thought 详情态

**核心功能**：

- 点击 Thought 卡片后进入详情态，左右分栏布局
- 左侧：正文编辑（Markdown）、Category 归属修改（多选）
- 右侧：Context 列表、双向链接列表
- 支持删除 Thought（二次确认）

**关键业务规则**：

- 详情态属于 Capture 主内容区，不让用户感觉进入了另一个产品
- 正文编辑区是主焦点，Context 和双向链接是辅助延伸区
- 关闭详情后必须回到原 Category、筛选和浏览位置，不能丢失滚动位置或重置筛选状态

---

### 模块：Context 管理

**核心功能**：

- 在 Thought 详情态右侧展示该 Thought 下的 Context 列表
- 每条 Context 显示：内容摘要、来源类型（个人经历 / 书籍 / 文章 / 视频 / 他人观点）、记录时间
- 支持展开查看完整内容、新增、编辑、删除单条 Context

**关键业务规则**：

- Context 不是独立节点，不参与图谱，不能被双向链接引用，始终附属于 Thought
- Context 列表以可扫描的摘要形式出现，不强迫用户进入系统整理流程
- 新增 Context 支持从 Thought 编辑区直接新增，也支持用户先搜索/浏览找到目标 Thought 再挂载

---

### 模块：双向链接

**核心功能**：

- 在 Thought 详情态右侧展示该 Thought 通过正文中 `[[title#id]]` 引用到的其他 Thought（引用了谁）
- 展示在正文中引用了该 Thought 的其他 Thought（被谁引用）
- 支持在 Markdown 正文中通过 `[[title#id]]` 语法直接建立对其他 Thought 的引用
- 点击关联 Thought 可跳转至对应 Thought

**关键业务规则**：

- 关联关系由系统根据正文中的 `[[title#id]]` 语法自动解析和维护，不需要用户离开编辑上下文进行手动添加/删除操作
- 双向链接在 Contemplate 图谱中呈现为连线，Capture 中只提供 backlinks 列表视图和跳转入口
- 沿双向链接做大范围关系探索是 Contemplate 的任务，Capture 只提供明确的跨模块出口
- 被引用 Thought 的删除需要处理 dangling links：当前 Thought 正文中保留失效的 `[[title#id]]` 标记，但视觉上提示该目标已不存在

---

### 模块：新建 Thought

**核心功能**：

- 点击「+ Idea」或「+ Insight」后，直接创建 Thought 并进入详情态
- Category 默认继承当前选中的 Category，可修改
- Idea 用于记录从具体经验或输入中得到的朴素结论
- Insight 用于记录通过关联、抽象或总结形成的更高层理解

**关键业务规则**：

- 创建后必须直接进入详情态，减少中间步骤，保护热状态
- 创建后新 Thought 必须立即出现在当前 Category 的列表中，让用户确认归属正确
- Insight 创建后可在正文中通过 `[[title#id]]` 引用已有 Thought，关联关系在图谱中呈现

---

## 7. 验收标准

### Journey 1 成功标准 → 验收条件

**成功标准**：

- 用户不需要先进入复杂管理流程，就能把新想法落到正确语境
- 创建过程足够短，不打断外部阅读、工作或复盘节奏
- 新 Thought 创建后能被当前 category 立即承接，之后可以被快速找回

**验收条件**：

- 用户从点击新建到进入可输入状态不超过 2 步（点击新建 → 进入详情态输入）
- 新创建的 Thought 默认归属当前选中的 Category，不需要用户在创建前额外选择分类
- 保存后新 Thought 立即出现在当前 Category 的 Thought 列表中
- 用户离开 Capture 后，通过重新选中同一 Category 能在 3 秒内找到新创建的 Thought

---

### Journey 2 成功标准 → 验收条件

**成功标准**：

- 用户能快速判断自己处在哪个 category 语境
- 用户能以合适密度浏览多个 Thoughts，靠少量信息完成回忆
- 用户打开和关闭 Thought 细节后，原 category、筛选和浏览位置仍然存在

**验收条件**：

- Category 树当前选中节点和页面标题共同显示用户所处的 Category 路径
- Thought 卡片在列表中单屏至少展示 6-8 条，且每条包含标题、3 行 Preview、类型标签、Context/双向链接数量和时间的摘要信息
- 用户关闭 Thought 详情后，列表恢复到原 Category、原筛选状态和原滚动位置
- 用户能在不打开详情的情况下，通过卡片信息判断一条 Thought 的性质和丰富度

---

### Journey 3 成功标准 → 验收条件

**成功标准**：

- Context 与当前 Thought 的关系清楚，不需要用户重新判断归属
- 用户能快速扫过 Context 摘要或关键信息，不被迫进入编辑或管理流程
- Context 不压过正文，用户仍然感觉自己停留在当前 Thought 的理解过程里

**验收条件**：

- Thought 详情态中，Context 列表与正文在同一屏可见（左右分栏或合理布局），用户不需要切换 tab 或滚动离开正文区域
- 每条 Context 至少展示内容摘要（50 字以内）、来源类型图标和记录时间，用户不展开就能判断这是什么来源
- Context 的新增入口在列表顶部或底部，不占用正文编辑区空间
- 双向链接列表与 Context 列表分区展示，链接列表的 visual weight 不高于 Context

---

### 通用验收条件

- Category 树的增删改操作完成后，其下 Thought 的归属关系正确更新，不出现 orphaned Thought
- 删除 Category 时触发二次确认，且明确告知用户其下 Thought 将归入父节点
- 搜索支持 Thought 正文和 Context 内容的全文匹配，实时高亮关键词
- 类型筛选、子分类范围切换和排序组合使用时，结果正确且状态可清除重置
- 正文中 `[[title#id]]` 引用的增删实时同步到 Contemplate 图谱，双向一致
