# Product Docs

`docs/1-product` 放的是 Reflecta 的产品工作流文档。这里的重点不是“按顺序填模板”，而是把产品判断拆成一组可独立调用的工作单元。

## 核心思路

拿到需求，PM 只做一件事：**不断缩小「我不知道的事」，直到可以动手。**

不确定性天然分两类：

```
阶段一：消除对用户的不确定性   →   我真的理解这个人在经历什么吗？
阶段二：消除对产品的不确定性   →   我知道该造什么了吗？
```

**阶段一没做完，不进入阶段二。** 不是流程规定——是因为阶段二的每一个判断，答案都藏在阶段一里。

阶段二的内部逻辑是：**先扩展解法空间，再收敛成产品决策，再落地成可交付的设计，最后定义验收标准。**

```
阶段一：理解用户
  1. 用户意图        我真的知道他想要什么吗？
  2. User Journey    我知道他在什么处境下追求这个结果吗？

阶段二：定义产品
  3. 解法空间        这个问题，世界上有没有好答案？       ← 扩展
  4. 产品决策        我们选什么解法、为什么、放弃什么？   ← 收敛
  5. 版本边界        这个版本做什么、不做什么？           ← 对齐
  6. 功能设计        具体怎么造？                         ← 落地
  7. 验收标准        怎么知道造对了？                     ← 验证
```

## 怎么用

先判断你现在缺的是什么，再进入对应文档，不要机械从 `1` 读到 `7`。

- 需求很模糊，不知道用户到底想要什么：先看 [1-用户意图.md]
- 已经知道目标，但场景不具体：看 [2-User-Journey.md]
- 在争论应该怎么做、能力该以什么形态出现：看 [3-解法空间.md] 和 [4-产品决策.md]
- 方向基本明确，但范围开始发散：看 [5-版本边界.md]
- 要进入设计或研发，需要把产品定义落具体：看 [6-功能设计.md]
- 需要判断 PRD 是否足够清楚、可验证：看 [7-验收标准.md]

## 推荐路径

从零开始写一份完整 PRD 时，默认路径是：

`用户意图 -> User Journey -> 解法空间 -> 产品决策 -> 版本边界 -> 功能设计 -> 验收标准`

但这只是常见路径，不是强制流程。如果输入已经足够清楚，就直接跳到当前缺的那一步。

## 使用原则

- 每篇文档只解决一个判断问题，不顺手替下一步补产物。
- 上一步的输出，才是下一步的输入。
- 如果缺少必要输入，先把缺口写出来，不要靠猜补全。
- 不要把用户场景直接翻译成功能入口或模块。
- 产品形态优先服务用户意图，而不是要求用户先理解产品结构。
