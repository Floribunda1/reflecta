# Graph Feature Set

> 日期：2026-06-16
>
> 状态：Draft
>
> 职责：基于 `graph-value-proposition.md` 推导 V1 Graph 的产品承载方式和最小功能集合。本文不承担视觉设计细节，不承担技术实现方案。

## 1. Value Proposition Input

Graph 的上游价值主张是：

> Graph 帮用户看见自己的个人理解正在形成怎样的认知结构。

它不是为了展示“我有多少笔记”，而是为了让用户回看时感受到：

> 我在某个领域已经理解到哪里了，哪些地方还浅，以及哪些理解正在通过 Connection 形成结构。

上游约束：

- Graph 不是数量统计面板。
- Graph 不是 AI 自动生成的关系网。
- Graph 不能只展示 Connection，而忽略 Context。
- Graph 不能把孤岛理解当成错误。
- Graph 不应该替用户判断掌握度。
- Graph 应该把用户带回回看、比较、补充和沉淀。

## 2. JTBD

当我已经在多个领域沉淀了一批个人理解，
但回看时觉得它们像散乱条目，不知道有没有形成结构，
我想知道哪些理解已经连起来、哪些仍然孤立、哪些缺少来源、哪些和其他理解有关，
以便决定下一步要补来源、补连接，还是沉淀更高层理解。

这个 JTBD 的重点不是“管理笔记”，而是：

> 通过回看个人理解的结构，找到下一次有效思考的入口。

## 3. Product Requirements

为了完成上述 JTBD，产品必须承载以下要求。

### 3.1 呈现个人理解

用户必须能看到自己已经沉淀的 Understanding。

这些 Understanding 是 Graph 的主体，不是外部资料、Context、标签或系统自动生成的摘要。

### 3.2 呈现显式关系

用户必须能看到 Understanding 之间已经存在的 Connection。

Connection 必须来自用户显式表达或确认，不能由系统自动推断后直接入库。

### 3.3 呈现孤岛

用户必须能看到哪些 Understanding 暂时没有连接。

孤岛不是错误，它表示该理解尚未被整合，可能是后续回看和补关系的入口。

### 3.4 呈现 Context 状态

用户必须能判断某条 Understanding 是否有 Context 支撑。

这里不需要抽象评分，但至少要让用户看出：

- 哪些理解有来源。
- 哪些理解缺少来源。
- 哪些理解需要回到原笔记补 Context。

### 3.5 呈现关联上下文

用户必须能看到某条 Understanding 和哪些其他 Understanding 有关。

这里的重点是 Connection 本身，而不是连接两端的 Category 是否相同。

Category / Domain 只作为关联的上下文信息：

- 用户可以知道连接两端分别属于哪些 Category。
- 如果连接两端的 Category 不同，这是 Connection 的附带信息，不是第一版的主叙事。
- 产品不应该把 Category 差异包装成独立功能或核心价值。

### 3.6 从观察回到整理

用户看到结构、孤岛或缺来源之后，必须能回到原 Understanding。

Graph 不是沉淀终点，它应该把用户带回：

- 补 Context。
- 补正文双链。
- 修正 Understanding。
- 沉淀更高层 Understanding。

### 3.7 控制全局复杂度

Graph 必须避免一打开就是不可理解的大网。

产品需要提供足够轻的方式，让用户缩小观察范围，但不能把第一版做成复杂检索系统。

### 3.8 支持 Domain-scoped Wander

用户必须能先锁定一个 Domain，再在该 Domain 内回看 Understanding。

这里的 wander 不是系统推荐，也不是 AI 帮用户判断哪些笔记值得看，而是通过视觉组织让用户自己看见回看线索：

- 当前 Domain 内的 Understanding 是主对象。
- 有显式 Connection 的 Understanding 应更容易形成局部组。
- 孤立 Understanding 必须可见，但不应被包装成错误状态。
- 与其他 Domain 有连接的 Understanding 应能让用户望见外部概念，但外部概念不能抢当前 Domain 主视觉。
- 默认不应铺满所有关系线；用户 hover / selected 后再强化局部关系。

产品要帮助用户自己产生判断：

> 这里好像有一组东西值得重新读。

而不是告诉用户：

> 系统认为这些笔记值得回看。

## 4. User Mental Model

Graph 可以借力的用户心智：

- 用户熟悉“笔记”。
- 用户熟悉双链 / backlink。
- 用户熟悉图谱里的节点和边。
- 用户理解一个节点可以代表一条笔记。
- 用户理解一条边可以代表引用或关系。
- 用户理解孤立节点意味着暂时没有连接。
- 用户理解点击节点查看详情。
- 用户理解用筛选缩小范围。
- 用户理解先进入一个领域，再在领域内游走回看。
- 用户可能熟悉 Obsidian / Roam / Logseq 的 graph 体验。

这个心智约束意味着：

> Graph 第一版应该尽量像一个笔记图谱，而不是重新发明一个需要解释的新产品系统。

## 5. Product Shape Options

Graph 的价值可以由多种产品形态承载。第一版需要先比较形态，再选择。

| Shape Option    | 如何承载价值                                                             | 主要风险                               |
| --------------- | ------------------------------------------------------------------------ | -------------------------------------- |
| 单画布笔记图谱  | 用节点和边直接展示 Understanding 与 Connection，并用节点状态表达 Context | 节点变多后可能产生视觉噪音             |
| 多栏 Topic Map  | 用领域、主题、笔记分层表达结构                                           | 第一眼主对象太多，容易像管理后台       |
| Dashboard       | 用状态卡片和统计概览表达积累情况                                         | 容易走向数量指标，偏离“个人理解结构”   |
| 对话式回看      | 通过 AI 问答帮助用户发现关系和边界                                       | 结构感不直接，也容易让 AI 代替用户判断 |
| 列表 + 局部关系 | 延续列表心智，在详情里展示关系                                           | 关系结构不够显性，Graph 的价值感弱     |

## 6. Shape Selection

第一版选择：

> 单画布笔记图谱。

选择理由：

- 它最直接承载 Understanding 和 Connection。
- 它借力用户已经熟悉的 graph / backlink 心智。
- 它的第一屏主对象很少：节点和边。
- 它能自然呈现孤岛：没有边的节点就是暂时独立的理解。
- 它能通过节点状态承载 Context；未连接通过没有边自然呈现。
- 它比 Dashboard 更不容易滑向数量统计。
- 它比多栏 Topic Map 更不容易变成管理后台。
- 它比对话式回看更能直接给用户结构感。

第一版不选择其他形态的原因：

| 不选形态        | 原因                                                       |
| --------------- | ---------------------------------------------------------- |
| 多栏 Topic Map  | 同时暴露领域、主题、笔记、详情，第一眼复杂度过高           |
| Dashboard       | 容易把价值表达成数量、比例、评分                           |
| 对话式回看      | 适合作为辅助探索，但不适合作为结构的第一视觉表达           |
| 列表 + 局部关系 | 可以复用在 Domain Workspace，但不足以验证 Graph 的独特价值 |

## 7. Selected Product Shape

### 7.1 第一屏

用户打开 Graph 后，第一眼看到：

- 一张图谱画布。
- Understanding 节点。
- Connection 边。
- 顶部轻筛选。
- 轻量图例。

第一屏不展示：

- 多栏管理后台。
- 主题分组列表。
- 常驻详情面板。
- 复杂统计 dashboard。

### 7.2 主对象

第一版只暴露两个主对象：

- Node：一条 Understanding。
- Edge：一条 Connection。

次级信息通过节点状态或点击详情出现：

- Category / Domain：节点标签、筛选范围、关联上下文。
- Context：节点状态 / 详情浮层。

### 7.3 核心动作

Graph 第一版只有四个核心动作：

1. 看图。
2. 筛范围。
3. 点节点。
4. 打开原笔记。

典型路径：

```text
打开 Graph
  -> 看到一张图
  -> 发现有些节点连起来，有些节点孤立
  -> 用 Category 筛选缩小观察范围
  -> 点击一个节点
  -> 查看标题、来源、所属 Category、连接状态
  -> 打开原笔记继续整理
```

## 8. Minimum Feature Set

| Feature            | 类型    | 承载的 Requirement                | 对应 JTBD                | 为什么必要                          |
| ------------------ | ------- | --------------------------------- | ------------------------ | ----------------------------------- |
| 单画布 Graph       | Core    | 控制复杂度并呈现整体结构          | 看见理解是否连成结构     | 没有画布就没有 Graph 的第一视觉表达 |
| Understanding 节点 | Core    | 呈现个人理解                      | 看见自己沉淀了哪些理解   | Understanding 是 Graph 的主对象     |
| Connection 边      | Core    | 呈现显式关系                      | 看见哪些理解已经连接     | Connection 承载用户已经意识到的关系 |
| 节点来源状态       | Core    | 呈现 Context 状态                 | 判断理解是否有根         | Reflecta 的差异在于理解有来源       |
| 孤立节点自然呈现   | Core    | 呈现孤岛                          | 看见哪些理解仍然独立     | 没有边本身就是孤岛表达              |
| 顶部轻筛选         | Core    | 控制全局复杂度                    | 按范围回看图谱           | 避免一打开就是不可理解的大网        |
| 节点详情浮层       | Core    | 呈现节点的具体 Context 和关系状态 | 判断理解是否有根         | 第一屏保持简单，点击后再看细节      |
| 打开原笔记         | Support | 从观察回到整理                    | 补来源、补连接、修正理解 | Graph 不是沉淀终点                  |
| 图例               | Support | 解释节点和边状态                  | 理解图谱状态             | 降低视觉状态的理解成本              |

## 9. Shape Rules

Shape Rule 不是 Feature。它们是为了让单画布笔记图谱不走偏而必须遵守的呈现规则。

| Shape Rule                  | 原因                                                             |
| --------------------------- | ---------------------------------------------------------------- |
| Context 不作为一级节点      | Context 是理解的根，不是一级知识对象                             |
| Category 不作为一级节点     | 第一屏主对象必须少，Category 只作为筛选范围和节点上下文          |
| Category 差异只是连接上下文 | Graph 的核心是 Connection，不是强调连接两端是否属于同一 Category |
| 第一屏不做多栏 Topic Map    | 避免用户同时理解太多对象                                         |
| 第一屏不展示统计卡片        | 避免 Graph 退化成数量 dashboard                                  |
| 节点状态只表达 Context      | 有 Context、无 Context；Connection 通过边表达，不表达掌握度评分  |

## 10. Support / Later / Not Now

### 10.1 Support

Support 是让 Core Feature 可理解、可信、可用的能力。

- 图例。
- 空状态。
- 基础布局稳定性。
- 画布缩放 / 平移。

### 10.2 Later

Later 是价值相关，但不进入第一版最小验证的能力。

- 自动 cluster 布局优化。
- 搜索和搜索结果定位。
- 时间演化视图。
- 局部图谱模式。
- 高级筛选。
- 保存视图。

### 10.3 Not Now

| 暂不做                        | 原因                                                                             |
| ----------------------------- | -------------------------------------------------------------------------------- |
| 多栏 Topic Map / 管理后台     | 第一版主对象过多，会弱化 Graph 的简单心智                                        |
| 笔记数量统计 dashboard        | 数量不能代表有效积累，也不能表达理解深浅                                         |
| 掌握度评分                    | 会替用户抽象判断知识边界，违背 Reflecta 的产品哲学                               |
| Graph 内手动关系管理后台      | 关系应在理解写作和回看中自然产生，不应变成独立管理系统                           |
| AI 自动创建 Connection 并入库 | 关系必须来自用户显式理解或确认                                                   |
| AI 自动推断关系并展示在图谱里 | 关系必须来自用户显式理解或确认，否则会让用户误以为这些关系已经属于自己的知识结构 |
| Context 独立节点库            | Context 是理解的根，不是一级知识管理对象                                         |
| 复杂 Category 关系分析页      | 第一版只需要呈现已有 Connection；Category 差异只是连接上下文                     |

## 11. Validation

### 11.1 行为指标

- 用户是否进入 Graph。
- 用户是否点击节点查看详情。
- 用户是否使用 Category 筛选缩小观察范围。
- 用户是否从节点详情打开原 Understanding。
- 用户是否从 Graph 发现无 Context 节点后补充 Context。
- 用户是否从 Graph 发现孤岛或相关节点后补充 Connection。

### 11.2 质性判断

Graph 成立时，用户应该能说：

- 我一眼知道这是我的笔记图谱。
- 我能看见哪些理解连起来了，哪些还是孤岛。
- 我能看见哪些理解没有来源。
- 我能点开节点，看它从哪里来、属于哪个 Category、连到了谁。
- 我能看见某条理解和哪些其他理解有关。
- 我会因为这些发现，回到原笔记补来源、补连接或修正表达。

## 12. Feature Set 结论

Graph 第一版选择单画布笔记图谱作为产品承载形态。

它的最小功能集合是：

1. 单画布 Graph。
2. Understanding 节点。
3. Connection 边。
4. 节点来源状态。
5. 孤立节点自然呈现。
6. 顶部轻筛选。
7. 节点详情浮层。
8. 打开原笔记。
9. 图例。

Category / Domain 不是单独 Feature，而是单画布 Graph 的上下文信息：

- Category 用于筛选图谱范围。
- 节点可以展示所属 Category，帮助用户理解这条 Thought 的背景。
- Connection 的重点是两条 Understanding 有关；如果连接两端的 Category 不同，它只是这条 Connection 的上下文。

这组功能共同验证：

> Graph 是否能让用户用熟悉的笔记图谱心智，看见自己的个人理解正在形成结构，并回到原笔记继续整理。
