# UX 文档写作规范

> 版本：v1.0
> 适用范围：所有模块的 UX 文档产出

---

## 文档定位

### 这份 UX 文档是什么

UX 文档是线框图开始**之前**必须完成的结构化设计判断文档。它的任务是把产品决策（PRD、功能文档）翻译成用户行为路径和界面判断，并在整个设计过程中作为所有决策的追溯依据。

UX 文档写完之后，线框图应该是「按图索骥」的产物，而不是探索性的头脑风暴。

### 这份 UX 文档不是什么

- **不是 PRD 的重复**：UX 文档不描述功能，而是描述用户在使用功能时的行为、感知和系统响应
- **不是视觉规范**：不涉及颜色、字体、间距
- **不是线框图的文字版**：UX 文档是线框图的前置依据，不是后置说明
- **不是技术异常清单**：UX 文档只描述用户能感知、且产品或技术前提已经成立的状态；不要凭通用 Web 模板假设 loading、error boundary、同步、冲突、失效、撤销等机制

### 产出时机

| 阶段         | UX 文档状态     | 用途                                 |
| ------------ | --------------- | ------------------------------------ |
| 线框图开始前 | 草稿完成        | 设计师与 PM 对齐范围、路径、关键判断 |
| 视觉稿评审前 | 终稿完成        | PM 和 design lead 审查决策依据       |
| 开发阶段     | 作为参照        | 实现 review 的对照标准               |
| 验收阶段     | 第 5 节直接抽取 | QA 使用验收条件                      |

### 阅读对象与关注点

| 读者           | 关注点                                              |
| -------------- | --------------------------------------------------- |
| 设计师（自己） | 写作即思考——逼迫自己把模糊判断写清楚                |
| PM             | 范围确认（1.2）、约束确认（1.3）、验收条件对齐（5） |
| 开发           | 设计意图、异常处理方式、状态清单                    |
| QA             | 验收条件（5）+ 异常场景（2.2、4）                   |

## 节间逻辑关系

五节不是独立的清单，而是一个连贯论证结构：

```
第 1 节（目标 + 范围 + 约束）
        ↓ 约束所有后续判断
第 2 节（信息架构 + 路径）
        ↓ 定义「空间」和「过程」
  第 3 节（节点细节）    第 4 节（路径外场景）
        ↓                      ↓
        第 5 节（验收条件）
   ↑ 每条条件必须追溯到第 1.1 节的某个障碍
```

**关键依赖规则：**

- 第 3 节的界面状态，必须能在第 2 节的路径中找到触发来源
- 第 4 节的边界场景，必须有对应的第 2 节路径来承接恢复逻辑
- 第 5 节的每条验收条件，必须能追溯到第 1.1 的某个障碍
- 所有状态和异常必须来自用户可感知的体验、产品决策或技术约束；不能因为模板里常见就默认写入

> 如果某个设计决策无法追溯到第 1 节，这个决策需要重新审视。
