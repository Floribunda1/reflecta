## 1. 产品目标

Reflecta PMF MVP 要验证：

> 用户能否把一次学习、实践或对话后的有效思考，沉淀成可追溯的个人理解；长期回看时，能否如实看到自己在某个领域里的理解、来源和显式关系。

MVP 不是 AI 产品，也不是图谱产品，而是：

> 一个能让个人理解带着来源和关系长期生长的最小系统。

这版产品不追求一次性生成完整洞察，也不追求自动整理用户所有材料。它要证明一个更基础的价值：用户愿意亲自沉淀自己的理解，愿意保留理解的来源，并在回看时感受到自己的知识网正在如实生长。

---

## 2. 目标用户

### 核心用户

持续学习、实践、复盘、和 AI 对话的深度思考者 / 知识工作者。

这类用户的典型状态：

- 经常看视频、读书、做项目、交易、搭建 workflow、和 AI 深聊。
- 不满足于收藏信息，希望形成自己的理解。
- 会被“我明明经历了很多，但没有真正长出来”刺痛。
- 在多个领域里有碎片化思考，希望长期看见自己的认知结构。

### 非目标用户

- 只想收藏材料、摘录内容、做稍后读的人。
- 只想让 AI 自动总结内容、替自己生成知识库的人。
- 以输入量、打卡量、阅读完成量为主要目标的人。
- 需要团队知识库、多人协作、内容发布系统的人。

---

## 3. Value Proposition

Reflecta 帮用户把学习、实践、观察和对话之后发生的有效思考，沉淀成有上下文、有边界、可回看的个人理解。长期回看某个领域时，用户能清楚看到自己对这个领域的理解是什么，以及这些理解分别从哪些经历、书籍、视频、实践和 AI 对话中长出来。

更短表达：

> Reflecta 帮你把学习、实践和对话，沉淀成可追溯的个人理解。

---

## 4. 产品原则

### 4.1 用户是大脑，AI 是辅助

用户完成理解和判断，AI 只能提供信息、建议、追问、对比和候选表达。

因此：

- 用户手动表达自己的理解，是整理和内化的一部分。
- AI 不应从原始材料中自动生成“用户的个人理解”并直接入库。
- AI 不应自动构建关系网并直接当作用户知识网。
- AI 的建议必须由用户理解、选择、修改和确认后，才可能进入知识网。

### 4.2 如实反映用户的知识网

MVP 不负责替用户判断知识边界、掌握度或薄弱点。

MVP 的最小成立逻辑是：

> 用户沉淀了什么，建立了哪些显式关系，产品就如实呈现什么。

### 4.3 孤岛不是错误

没有关系的理解可以独立存在。

孤岛只表示这条理解尚未被整合，不代表用户做错了，也不代表系统必须自动补关系。

### 4.4 关系是理解的一部分

当用户意识到两个理解之间有关系时，这个“意识到关系”的瞬间本身就是一次有效思考。

关系可能在两个时刻产生：

- 用户写下新理解时，自然意识到它和已有理解有关。
- 用户后续回看整理时，突然意识到两个理解其实在同一条链条上。

产品必须支持这两种时机。

## 5. 核心对象语义

这些对象可以沿用 Reflecta 现有概念，但 PRD 重新定义它们在 PMF MVP 中的产品语义。

### Thought：个人理解

Thought 不是普通笔记条目，而是用户形成的一个个人理解。

它可以是：

- 判断：我现在相信什么。
- 触动：某个材料为什么击中了我。
- 困惑：我意识到一个还没想清的问题。
- 教训：一次实践后我学到了什么。
- 模型雏形：我开始看见某类问题的结构。

规则：

- Thought 必须由用户主动创建或确认。
- Thought 可以暂时没有 Connection。
- Thought 可以被后续修改，因为理解会随经历和回看修正。

### Context：理解的来源上下文

Context 是这个理解从哪里长出来。

它不是附件，也不是普通来源字段。它要帮助用户未来回到现场，知道当时为什么形成这个理解。

Context 可以来自：

- 个人实践
- 书籍
- 视频
- 文章
- 他人观点
- AI 对话
- 项目经历
- 交易复盘

规则：

- 一个 Thought 可以有多个 Context。
- Context 应尽量保留“为什么触发我”，而不是只保留 source type。
- Context 可以后续补充和修正。

### Category：领域语境

Category 是用户回看某个领域理解的语境。

它不是单纯文件夹，也不是对象管理分类。它回答：

> 我在这个领域已经形成过哪些理解？

规则：

- Thought 可以归属一个或多个 Category。
- Category 用于沉淀时放入语境，也用于回看时盘点领域理解。
- MVP 不要求复杂领域体系，但必须支持用户按领域回看。

### Connection：用户显式意识到的理解关系

Connection 是用户显式表达的理解关系。

它可以来自：

- 用户在写 Thought 时引用已有 Thought。
- 用户回看整理时补充关系。
- 用户修正旧理解时调整关系。

规则：

- Connection 不应由 AI 自动创建并直接入库。
- AI 建议关系属于 PMF Later，且必须由用户确认。
- Connection 可以后续增加、调整或移除。

## 6. MVP 用户路径

### Journey A：沉淀个人理解

**用户处境**

用户刚经历一次学习、实践、观察或对话，并已经意识到其中有一个值得留下的个人理解。

**任务路径**

1. 用户进入沉淀入口。
2. 用户用自己的语言写下这个理解。
3. 用户记录这个理解从哪里来。
4. 用户把这个理解放入一个领域语境。
5. 如果用户当下意识到它和已有理解有关，用户连接已有理解。
6. 如果用户暂时没有意识到关系，理解独立保存。
7. 保存后，这条理解进入用户的长期知识网。

**成功标准**

- 用户感觉自己是在记录一个理解，而不是填写一个知识管理对象。
- 用户能保留理解的来源，而不是只留下抽象结论。
- 用户能把理解放入以后可回看的领域语境。
- 用户不被强迫建立关系。

### Journey B：回看领域理解

**用户处境**

用户一段时间后回到某个领域，想知道自己已经理解了什么。

**任务路径**

1. 用户进入某个领域语境。
2. 用户看到该领域下已有的个人理解。
3. 用户能看到每个理解从哪里来。
4. 用户能看到理解之间已显式建立的关系。
5. 用户能区分哪些理解已经连接，哪些暂时独立。
6. 用户获得“原来我对这个领域的理解是这些，它们来源于这些经历和材料”的盘点感。

**成功标准**

- 用户不是只看到内容列表，而是能盘点领域内已有个人理解。
- 用户能看到理解和来源之间的关系。
- 用户能看到理解之间的显式关系。
- 用户不需要系统自动评分，也能感受到知识网被如实呈现。

### Journey C：后续整理和修正

**用户处境**

用户回看时产生新的理解，发现旧理解需要补充、修正或连接。

**任务路径**

1. 用户打开已有理解。
2. 用户修改理解表达。
3. 用户补充或修正来源上下文。
4. 用户补充与其他理解的关系。
5. 用户调整或移除不再成立的关系。
6. 用户保存后，知识网结构随之更新。

**成功标准**

- 用户能修正过去的理解，而不是只能追加新内容。
- 用户能补来源、补关系。
- 知识网能随着用户新的理解自然生长。

## 7. MVP 功能设计

### 7.1 个人理解沉淀

**核心功能**

- 用户能创建一条个人理解。
- 用户能用自己的语言填写理解内容。
- 用户能保存后再次编辑。
- 系统允许理解没有关系时独立存在。

**关键业务规则**

- 创建入口必须以“写下个人理解”为主，不得把用户首先带入复杂字段填写。
- 系统不得要求用户必须先选择关系才能保存。
- 系统不得自动把 AI 总结内容作为用户理解入库。
- 用户保存后，内容必须能在对应领域回看中出现。

### 7.2 来源上下文记录

**核心功能**

- 用户能为一个理解记录来源上下文。
- 用户能选择或填写来源类型，例如实践、书籍、视频、文章、AI 对话、他人观点。
- 用户能记录来源名称或场景描述。
- 用户能记录“为什么这个来源触发了我”。
- 用户能后续补充、修改或删除来源上下文。

**关键业务规则**

- 来源上下文必须和某个个人理解关联。
- 来源上下文不应被设计成独立知识节点。
- 来源字段不应只停留在 source type；必须给用户保留具体场景和触发原因的空间。
- 用户可以先保存理解，再补充来源上下文，但回看时应清楚看见哪些理解已有来源、哪些来源较薄。

### 7.3 领域语境组织

**核心功能**

- 用户能把个人理解放入一个或多个领域语境。
- 用户能创建、重命名、调整领域语境。
- 用户能在沉淀时选择领域。
- 用户能在回看时进入某个领域。

**关键业务规则**

- 领域语境服务于回看“我对这个领域理解了什么”，不得只被设计成对象管理分类。
- 用户可以先使用临时或较粗的领域语境，后续再调整。
- 一个理解可以归属多个领域。

### 7.4 用户显式关系表达

**核心功能**

- 用户能在写理解时连接已有理解。
- 用户能在回看整理时补充关系。
- 用户能查看一条理解连接了哪些已有理解。
- 用户能移除或调整关系。

**关键业务规则**

- 关系必须来自用户显式表达或用户确认。
- 系统不得自动创建关系并直接入库。
- 没有关系的理解必须允许保存。
- 关系表达不应被设计成每次沉淀必填的表单步骤。

### 7.5 后续整理和修正

**核心功能**

- 用户能编辑已有个人理解。
- 用户能补充或修改来源上下文。
- 用户能补充、修改或移除关系。
- 用户能调整领域归属。

**关键业务规则**

- 后续修正是 Core，不是高级编辑功能。
- 用户修正内容后，回看视图和知识网呈现必须同步更新。
- 系统不得把旧内容锁死成不可更改的记录。

### 7.6 领域内回看

**核心功能**

- 用户能进入某个领域，看到该领域下已有个人理解。
- 用户能看到每条理解的来源上下文摘要。
- 用户能看到每条理解的显式关系摘要。
- 用户能打开某条理解查看完整内容、来源和关系。
- 用户能从回看中进入编辑 / 补来源 / 补关系。

**关键业务规则**

- 领域回看必须服务“我在这个领域已经理解了什么”，不得退化成普通内容列表。
- 回看视图必须同时暴露理解、来源和关系三个层面。
- 不要求 MVP 自动识别薄弱点或生成领域总结。

### 7.7 个人知识网呈现

**核心功能**

- 产品能呈现用户已沉淀的个人理解。
- 产品能呈现理解与来源上下文的关系。
- 产品能呈现理解之间由用户显式表达的关系。
- 产品能区分已连接理解和独立理解。

**关键业务规则**

- 知识网呈现的核心是如实反映，不是自动推断。
- 视觉形态可以是图谱、列表、局部关系视图或组合形态；PRD 不在此处锁死 UI。
- 如果采用图谱，图谱必须服务理解、来源和显式关系的回看，不得只是视觉展示。
- 如果采用列表或领域视图，也必须保留关系和来源可见性，否则无法兑现知识网价值。

## 8. Support Features

Support Features 只支撑 Core 跑通，不扩大产品边界。

### 8.1 查找已有理解

**支撑目标**

用户在表达关系时，需要找到要连接的已有理解。

**功能要求**

- 支持按关键词查找已有理解。
- 支持在连接关系时快速选择已有理解。
- 搜索结果应显示足够上下文，避免用户连错对象。

### 8.2 基础编辑入口

**支撑目标**

用户后续修正理解、补来源、补关系。

**功能要求**

- 用户能从回看路径进入编辑。
- 用户能从单条理解详情进入编辑。
- 编辑后回到原语境，不丢失当前位置。

### 8.3 基础浏览 / 过滤领域内容

**支撑目标**

用户回看某个领域下已有理解。

**功能要求**

- 支持按领域进入内容范围。
- 支持在领域内查看理解列表或结构。
- 可支持基础类型、时间或关键词筛选，但不作为 MVP 价值重点。

### 8.4 持久保存与可靠数据结构

**支撑目标**

长期积累必须稳定可信。

**功能要求**

- 用户创建、编辑、删除、连接关系后，数据可靠保存。
- 应避免关系、来源、领域归属出现明显丢失或不一致。

## 9. PMF Later

这些能力贴近 Reflecta 长期方向，但不进入 PMF MVP。

| Later | 原因 |
| --- | --- |
| AI 辅助澄清表达 | 贴近 value proposition，但手动沉淀和回看闭环要先成立 |
| AI 提醒补充来源上下文 | 有助于提高沉淀质量，但 PMF 先验证用户是否愿意主动保留来源 |
| AI 建议可能关系 | 有助于发现连接，但必须建立在用户主导关系之后 |
| 自动识别薄弱理解 | 重要的下一阶段能力，但 MVP 先做到如实呈现知识网 |
| 心智模型聚合 / 领域结构洞察 | 贴近长期愿景，但需要足够沉淀数据作为基础 |

---

## 10. Non-goals / Never

这些方向会破坏 Reflecta 的产品哲学，不应作为后续路线。

| Never | 原因 |
| --- | --- |
| AI 替用户自动生成“个人理解”并直接入库 | 违背“用户是大脑，AI 是辅助”；绕过用户自己的理解和表达过程 |
| AI 自动构建关系网并直接当作用户知识网 | 关系必须来自用户显式理解；AI 推断最多只能作为建议 |
| 用输入量、打卡、收藏量作为核心激励 | 会鼓励无效积累，偏离“有效思考沉淀” |

## 11. 和现有模块的关系

### Capture

MVP 中，Capture 承担沉淀个人理解和局部整理职责。

它应支持：

- 创建个人理解。
- 补充来源上下文。
- 放入领域语境。
- 在表达过程中连接已有理解。
- 编辑已有理解。
- 补来源、补关系。

Capture 不应变成复杂知识管理后台，也不应强迫用户在创建时填写所有字段。

### Contemplate / 领域回看

MVP 中，Contemplate 或新的领域回看能力承担回看和知识网呈现职责。

它应支持：

- 进入某个领域语境。
- 查看该领域下个人理解。
- 查看每条理解的来源上下文。
- 查看用户显式建立的关系。
- 从回看中进入整理和修正。

Contemplate 不一定必须是全局图谱。它的职责是如实呈现个人知识网，而不是展示某种固定视觉形态。

### Agent

Agent 不进入 PMF MVP Core。

它可以作为 Later，在用户已经有理解之后辅助澄清、补充来源、建议关系。但它不能替用户生成个人理解或自动构建知识网。

## 12. 验收标准

### Journey A：沉淀个人理解

**成功标准**

- 用户能用自己的语言写下一个刚形成的理解。
- 用户能记录这个理解来自哪次学习、实践或对话，以及为什么触发自己。
- 用户能把理解放入领域语境。
- 用户能在意识到关系时连接已有理解。
- 用户能在没有关系时独立保存。

**验收条件**

- 系统提供创建个人理解的入口，并允许用户保存自己输入的理解内容。
- 系统支持为个人理解记录来源类型、来源名称或场景描述、触发原因。
- 系统支持为个人理解选择至少一个领域语境。
- 系统支持用户连接已有理解，但不要求必须连接。
- 一条没有关系的个人理解可以保存成功，并能在对应领域回看中出现。

### Journey B：回看领域理解

**成功标准**

- 用户能回到某个领域，看到已有个人理解。
- 用户能看到这些理解分别来自哪些来源上下文。
- 用户能看到已显式建立的关系。
- 用户能区分已连接理解和独立理解。

**验收条件**

- 系统提供按领域回看的入口。
- 领域回看中展示该领域下的个人理解。
- 每条理解可查看来源上下文摘要或详情。
- 每条理解可查看与其他理解的显式关系。
- 没有关系的理解仍然在领域回看中可见。

### Journey C：后续整理和修正

**成功标准**

- 用户能修改旧理解。
- 用户能补充或修正来源上下文。
- 用户能补充、调整或移除关系。
- 修改后，领域回看和知识网呈现同步更新。

**验收条件**

- 系统支持编辑已有个人理解。
- 系统支持新增、编辑、删除来源上下文。
- 系统支持新增、调整、移除理解之间的显式关系。
- 用户修改后再次进入领域回看，能看到更新后的理解、来源和关系。

## 13. PMF 验证指标

这些指标用于验证 MVP 是否支撑 value proposition，不作为增长指标。

### 行为指标

- 用户是否创建了多条个人理解。
- 用户创建个人理解时，是否愿意记录来源上下文。
- 用户是否把个人理解放入领域语境。
- 用户是否主动建立显式关系。
- 用户是否回看某个领域。
- 用户是否在回看后修改理解、补来源或补关系。

### 质性判断

用户使用后是否能说出：

- “我对这个领域的理解是这些。”
- “这些理解分别来源于这些经历、材料和对话。”
- “有些理解已经连起来了，有些还只是独立存在。”
- “我能回头修正旧理解，而不是重新开始。”

### 不采用的指标

- 输入条数越多越好。
- 打卡天数越多越好。
- AI 生成内容越多越好。
- 自动关系越多越好。

这些指标会把产品推向无效积累。
