# Skill：翻译用户意图

## 这个技能是什么

拿到一个需求描述时，你的第一反应往往是「用户需要一个 XX 功能」。

这个反应几乎总是错的。

**翻译意图**，就是把需求材料里的表层动作，挖到用户真正想完成的事。它是写 PRD 的第一步，也是最容易跳过、跳过之后最难补救的一步。

---

## 为什么这一步容易出错

表层动作是可见的，意图是隐藏的。

需求材料通常这样写：「用户希望能搜索历史记录」「用户需要批量导入文件」「用户想让系统推荐方案」。

这些描述都是**动作**，不是**目标**。直接把动作翻译成功能，产品就会变成一堆操作入口——用户要先理解你的模块，才能开始完成自己的事。

---

## 怎么做：两个追问

对每一个表层动作，连续追问两个问题：

**① 用户为什么要做这件事？**
→ 找到驱动这个动作的真实处境

**② 完成之后他得到了什么？**
→ 找到他真正想拿走的结果

两个问题都答出来，才算翻译完成。

---

## 练习：从动作到意图

| 表层动作       | ❌ 错误翻译            | ✅ 正确翻译                          |
| -------------- | ---------------------- | ------------------------------------ |
| 看数据看板     | 用户需要一个看板页面   | 知道哪里异常、下一步处理什么         |
| 批量导入文件   | 用户需要一个导入功能   | 快速完成录入，知道哪些需要修正       |
| 搜索历史记录   | 用户需要一个搜索页     | 找回和当前任务相关的依据             |
| 让系统推荐方案 | 用户需要一个推荐模块   | 减少判断成本，但保留最终决定权       |
| 生成报告       | 用户需要一个报告生成器 | 把已有材料组织成可提交、可修改的成果 |

注意观察「正确翻译」的结构：它描述的是**用户处于什么状态**，以及**他想离开这个状态去哪里**。

---

## 一个完整示例

**原始需求：**

> 招聘团队每天收到大量简历，希望系统能自动匹配岗位要求、打分排序、推荐面试候选人。

**追问过程：**

- 他们为什么要这件事？→ 简历太多，逐份精读来不及
- 完成之后他们得到了什么？→ 知道谁值得约面试，知道为什么值得

**翻译结果：**

```
❌ 错误：用户需要一个简历智能筛选功能

✅ 正确（拆成三层意图）：
   过滤：我想快速排除明显不符合要求的简历
   判断：我想知道候选人和岗位的匹配点在哪里
   决策：我想在有限时间内决定谁值得约面试
```

注意：一个需求背后可能有**多层意图**，要分别写出来，不要合并成一句话。

---

## 输出格式

翻译完成后，用这个格式写下来：

```
意图名称（用户自己会这样描述自己的目标）
└── 用户处境：他正处于什么状态，面对什么压力
└── 想要结果：他想拿走什么，或者离开什么状态
```

**示例：**

```
意图：在有限时间内决定谁值得约面试
└── 用户处境：今天有 20 份新简历，没有时间逐份精读
└── 想要结果：快速判断出值得推进的候选人，有依据，能说清楚
```

### 补充 Case（必选）

每个意图下面必须跟一个 **Case**，用一个具体的用户场景把抽象的意图翻译成"可感知、可验证"的事实。Case 不是重复意图，而是让团队读完之后能**感受到用户当时的处境**。

Case 的写法：

```
**Case**：

> 用户……（具体场景：谁在什么情况下、做了什么、遇到了什么、最后得到了什么）
```

**好 Case 的标准：**

- 有具体的人、具体时间、具体数字（"用户两周前记录了 12 条 Thoughts"，而不是"用户积累了很多内容"）
- 包含一个**转折或张力**（用户原以为……，结果发现……；用户想……，但面临……）
- 能追溯到具体的产品对象或界面（"用户在 Capture 中选中 Category"，而不是"用户在使用系统"）
- 读完之后，团队能判断"如果这个意图成立了，Case 里的用户应该有什么样的行为变化"

**示例：**

```
意图：新想法出现时，立刻把它放进正确语境，不打断当前节奏
└── 用户处境：用户刚看完一段视频、踩过一个坑、或工作中突然闪过一个判断，需要立刻记下来
└── 想要结果：这个想法被记录在一个明确的 category 下，之后能靠 category 快速找回

**Case**：

> 用户在看一个关于"行为设计"的视频时，突然意识到"环境提示比意志力更可靠"。用户立刻打开 Reflecta，左侧 Category 树已经选中"行为设计"，点击「+ Idea」后直接输入这条判断的核心内容，保存后新 Thought 立刻出现在列表中。整个过程不超过 30 秒，用户没有被打断看视频的节奏，也确信这个想法之后能通过"行为设计"这个 category 快速找回。如果当时要先选分类、填表单、再进编辑器，这个想法很可能就因为流程太长而被放弃记录了。
```

**为什么必须写 Case：**

- 意图是抽象的，Case 是具体的。没有 Case，团队对"用户处境"的理解会各自不同。
- Case 是后续 Journey、解法空间和产品决策的**共同参照点**。当团队争论"这个功能做不做"时，回到 Case 问"Case 里的用户需要这个吗"。
- Case 也是验收标准的来源。验收条件本质上就是在问"Case 描述的情景，系统现在能支撑了吗"。

**常见错误：**

- ❌ Case 写成功能描述："用户点击按钮，系统弹出面板，用户输入内容后保存"。这是动作，不是场景。
- ❌ Case 缺少张力："用户使用系统记录想法，然后找回了想法"。太平淡，无法驱动设计决策。
- ❌ Case 和意图脱节：Case 描述的场景无法由当前意图解释。这说明意图翻译错了，或者 Case 选错了。

## 自检：一个判断标准

翻译完成后，问自己一个问题：

> **这句话，用户自己会不会这样描述自己的目标？**

如果你写的是「用户需要一个 XX 功能」，答案一定是不会。
如果你写的是「我想在有限时间内决定谁值得约面试」，用户会点头。

通过这个检验，才算翻译完成。

---

## 常见错误模式

**错误一：把动作当意图**

> ❌「用户想要筛选简历」→ 这是动作，不是意图

**错误二：把系统能力当用户目标**

> ❌「用户需要 AI 打分排序」→ 这是手段，不是目标

**错误三：意图写得太宽泛，无法驱动设计决策**

> ❌「用户想提高效率」→ 这不能告诉你做什么、不做什么

**判断标准：** 写出来的意图，能不能让你判断「某个功能做还是不做」？能，才是有效的意图。
