## 1. 业务背景

### 1.1 为什么存在

Reflecta 帮助用户把学习、实践和对话后的有效思考沉淀成「理解」（Understanding）。随着理解越积越多，用户回看时遇到两个问题：

1. **理解是散乱的**：列表里的条目看不出逻辑关系——谁依赖谁、谁推导出谁、谁与谁矛盾。
2. **关系缺乏语义**：旧的知识图谱只显示"连了没有"，不显示"为什么连"；且关系是系统推断的，用户说不清也不认同。

用户真正需要的是：**亲手把理解摆出来，亲手标记它们之间的关系**，从而看清一个领域的心智结构——我理解了什么、哪些已经连成结构、哪些还是孤岛、下一步该补哪里。

### 1.2 服务什么场景

- **回看整理**：学完一个主题（如行为设计、交易心理、LLM Agent）后，把相关理解拖到一张画布上，摆出结构。
- **结构推导**：标记"B 依赖 A""C 由 A 推导而来"，让理解之间的逻辑链条显性化。
- **发现缺口**：看着画布发现哪些理解还是孤岛、哪个环节缺一块，决定下一步沉淀什么。
- **复用与关联**：同一张理解卡可以出现在多个画布（引用而非复制），一个理解在不同心智结构里各自发挥作用。

### 1.3 产品原则（不可走偏）

- **关系来自用户显式标记**：连线、标签、分组都由用户亲手完成；系统不自动推断关系。
- **用户是大脑**：画布是用户思考的载体，不是 AI 自动生成的图。
- **理解是引用**：画布上的理解卡引用理解库，不产生副本；被引理解删除后显示占位，不静默丢卡。

### 1.4 画布 × Agent 的协作主张（核心心智与产品主张）

#### 出发点：旧流程把最难的认知劳动压在了用户身上

用户过去在 Obsidian Canvas 式白板上的典型流程是：

```text
把冒出的想法摆成卡片（孤岛） → overview 全局 → 盯着孤岛等脑子里“迸发出心智” → 自己连线
```

这个流程的问题：**“从孤岛中看出结构”这个最难的认知劳动，完全由用户承担**——靠灵感迸发、靠运气，时灵时不灵；而且在与 AI 对话时，AI 其实已经把全部卡片读进上下文、在内部形成了组织连线，但**这些关联活在对话里，不可见、不可检查、不可编辑**，用户“感觉 AI 关联了很多东西，但脑子里是糊的，也没有一个地方可以看它们的关联关系”。

#### 核心主张：AI 是提案者，用户是裁判者

画布出现后，协作形态发生根本变化——**灵感引擎从用户转移到 AI，用户从“发作者”变成“裁判”**：

- 用户不再需要“突然迸发灵感、发现两个东西原来是这么一回事”。
- 用户只需要：**提供一个隐隐的线头**（“这个是不是就是那个”），以及**用 taste 诊断 AI 的提案**（这个对还是不对）。
- AI 负责：基于当前画布的孤岛 + 用户的线头 + 它已经读过的上下文，**推荐一个心智模型结构**（谁依赖谁、谁是核心、谁是边界、怎么分组），并**把它的内部连线显式化**。

这条主张与产品原则完全对齐：**判断（taste）是用户最擅长、AI 最不该代劳的**；AI 的关联从“对话里隐式”变成“画布上显式、可诊断、可编辑”。

#### 协作主线（完整流程）

```text
① 孤岛阶段：用户在画布上摆卡片 / 理解库里已有散落理解，形成孤岛
② 线头输入：用户带着一个模糊直觉来找 AI（“这个是不是就是那个”）
③ AI 提案：AI 读当前画布结构 + 线头 + 已有上下文，推荐一个心智结构提案
   ——带理由（为什么这样连、为什么这样分组），让用户能高效判断
④ taste 诊断：用户判断“对 / 不对 / 哪里不对”，与 AI 迭代修正
⑤ 认可落画布：认可后结构落到画布上，两条路径并存——
    a) AI 更新画布（在现有画布上增 / 连 / 分组）
    b) 用户自己拖卡片、自己连线
```

#### 设计含义（不压缩）

1. **核心动作是“推荐心智模型”，不是“整理画布”**：AI 提案的是结构判断（A 依赖 B、C 是核心、D 是边界），不是把卡片摆整齐。
2. **提案的输入 = 当前画布结构 + 用户的线头**：孤岛必须先能被 AI 读到（读画布能力）；用户的直觉要能传进对话。
3. **认可后是“改现有画布”，不是“新建一张画布”**：AI 更新画布 = 在现有画布上增元素、连关系、打分组。
4. **提案必须“可见、可诊断”**：光有文字说明不够——用户要能看到结构预览（卡片、连线、分组）、能反驳（“这条不对，去掉”）、能逐条接受或拒绝。
5. **两种协作入口并存，不做二选一**：
   - 对话侧沉淀：在全局 Chat 深聊到结构成型时，把当前讨论的关联沉淀成 / 更新画布；
   - 画布侧就地协作：在画布里打开 Chat 侧边栏，AI 以当前画布为作用域，边看画布边聊边组织。
6. **判定标准**：用户不再需要“突然迸发灵感”——只需要提供线头 + 用 taste 验收；画布是 AI 关联的“可见容器”，用户永远是最终编辑者。
7. **成果可见性（C14）**：每个对话提供 artifact panel，聚合本对话已落地的产出（understanding / context / canvas），让“这条对话产出了什么”可见；UX / UI 后议，进 v1。

### 1.5 与双链（wiki-link / Connection）的关系定位

画布连线与现有双链**不重复，分层共存**：

|          | 双链（引用网）                                 | 画布连线（结构网）                       |
| -------- | ---------------------------------------------- | ---------------------------------------- |
| 语义     | 「我提到过 X」（弱引用）                       | 「X 在我的结构里处于什么位置」（强语义） |
| 形态     | 无向、无类型、无标签，正文 `[[u:id]]` 自动解析 | 有向、带标签、带样式，用户显式搭建       |
| 产生时机 | 写作时隐式产生                                 | 回看时显式搭建                           |
| 作用域   | 全局                                           | 画布局部                                 |
| 服务     | 回溯来源                                       | 看清结构                                 |

**调研结论（2026-08-11）**：社区对两者关系的处理有三种模式——分离（Obsidian：画布箭头纯视觉、与链接零互通）、统一（Scrintal：画布箭头与正文链接是同一关系）、部分统一（Heptabase：正文 backlink 可导入白板做视觉整理；Logseq：白板图形可链接块但双向同步有缺陷）。

**我们的选择：分层 + 素材互通（Heptabase 式）**，依据：

1. **不能统一**：画布连线是**画布局部**的——同一对理解在不同画布可标不同关系（如一个画布标「推导出」、另一个标「矛盾」）；统一成全局关系必然冲突。
2. **不能纯视觉分离**：我们的连线承载语义（有向 + 标签 + 样式），放弃语义等于放弃画布核心价值。
3. **素材互通，数据不互通**：
   - 从理解库拖入理解卡时，提示该理解已有的双链（参考现有引用决定如何连线，但连不连、标签是什么由用户定）。
   - 理解详情显示「该理解出现于哪些画布」（反向查询已有索引，见 M6-6）。
   - 正文引用不自动画线；画布连线不写回 `understanding_connections`（守住「关系来自用户显式标记」，也避免双向同步的维护泥潭）。

**引用网降级为背景功能（2026-08-15 定）**：

- **本体论区分**（详见共识 C16）：引用网是「文档说了什么」（**事实**，自动解析，无结构含义承诺）；画布连线是「你相信什么」（**信念**，显式搭建，结构承诺）。产品要保真的、用户要负责的、画布要承载的，都是后者。
- **wiki-link 的产品定位**：保留，但降级为**溯源（provenance）+ 素材**，不是关系主界面；关系主界面 = 画布结构网（"为什么/怎么连"）。
- **社区验证**：全局图谱被广泛批评为 show-off（vault 超过几十个文件即无法导航）；链接只表达"有关系"（THAT），不表达"什么关系"（WHY/HOW）——画布连线恰好补上这一层；AI 检索正在让手工双链导航变得不必要。
- **产品可见修正**：理解列表的「N 个双链关系」文案改为「N 条引用」；正文 `[[u:]]` 在 UI 与工具输出中一律以"引用 / mention"语义呈现，不暗示结构关系。
- **概念根源修正（实施层，见共识 TBD-3）**：表名 `understanding_connections` 改为 `understanding_mentions`；删除 agent 的 `graph` tool 与 CLI `reflecta graph`（wiki-link as graph 概念）；Agent 看到 wiki-link 只能当溯源线索，不能当结构（结构推理以画布为准）。

### 1.6 一句话定位

> 理解画布是一个无限画布：一张画布承载一个心智结构，文本卡与 Reflecta 内部元素可自由摆放与连线，用户亲手标记"谁依赖谁、谁推导出谁"。

## 2. 功能模块

本版实现划分为 **8 个模块**，按职责与依赖关系组织：

```text
┌──────────────────────────────────────────────────────────────┐
│ 模块一：画布管理（入口）                                      │
│   画布列表：新建 / 重命名 / 删除，进入画布                    │
└──────────────┬───────────────────────────────────────────────┘
               ▼
┌──────────────────────────────────────────────────────────────┐
│ 模块二：画布工作区（主舞台）                                  │
│   工具栏 + 无限画布 + 左下控制 + 缩略图 + 搜索 + 导出         │
└───────┬────────────────────────────────┬─────────────────────┘
        ▼                                ▼
┌────────────────────────┐  ┌─────────────────────────────────┐
│ 模块三：元素体系        │  │ 模块四：关系与连线              │
│ 理解卡 / 文本卡 / 组 /  │  │ 有向连线 + 自由标签 + Handle   │
│ 画布引用                │  └─────────────────────────────────┘
└───────────┬────────────┘
            ▼
┌──────────────────────────────────────────────────────────────┐
│ 模块五：理解库面板（右侧单面板 · 库模式）                     │
│ 领域过滤 + 搜索 + 排序 + 理解列表 → 拖入画布                  │
└───────────┬──────────────────────────────────────────────────┘
            │ 互斥切换（同一面板槽位）
            ▼
┌──────────────────────────────────────────────────────────────┐
│ 模块六：理解详情联动（右侧单面板 · 详情模式）                 │
│ 点击理解卡 → 详情编辑 → 保存后画布卡片同步                    │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 模块七：编辑体验与数据（贯穿全部）                            │
│ React Flow 行为基准 / 交互反馈 / 业务删除 / 文档持久化       │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 模块八：Agent 画布协作（AI 提案者 / 用户裁判者）              │
│ 读（read/list/search）+ 写（create/update/delete，审批制）    │
│ + 展示（draft-preview）+ 引用（[[cv:]] + 只读 Modal）          │
│ + 成果可见性（artifact panel）                               │
└──────────────────────────────────────────────────────────────┘
```

### 模块关系

- **模块一**是入口：用户从这里进入任意画布。
- **模块二**是主舞台：承载所有元素与连线的展示和操作。
- **模块三、模块四**是内容本体：元素是"有什么"，连线是"怎么关联"。
- **模块五、模块六**是内容的进出通道：理解从理解库拖入画布（模块五），点击卡片回到理解详情编辑（模块六）；两者共用右侧同一面板槽位，互斥切换。
- **模块七**是体验与数据底座：编辑体验能力贯穿模块二三四，持久化保证一切变更可恢复。
- **模块八**是 Agent 协作层：读（理解心智结构）、写（内容级、审批制）、展示（draft-preview 验收界面）、引用（`[[cv:]]` + 只读 Modal）、成果可见性（artifact panel）——承载「AI 提案者 / 用户裁判者」协作主张的落地。

### 模块三：元素体系

**共同尺寸规则**：理解卡、文本卡、组、画布引用全部显式采用 React Flow `NodeResizer`，均可自由调整宽高；只读态不可调整，尺寸随画布持久化。

| #     | 功能     | 产品要求                                                                                                          |

| M3-D4 | 解组     | 选中组后，按 Cmd/Ctrl+Shift+G 或从 selection 右键菜单选择「解组」；组容器消失，成员保留并维持画布位置             |

| M3-D6 | 嵌套     | selection 中可以包含组；对其再次打组形成嵌套组，层级不限                                                          |

### 模块四：关系与连线

### 模块八：Agent 画布协作（AI 提案者 / 用户裁判者）

> 承载「提案-诊断-落画布」协作闭环（见 §1.4）。**写操作全部经用户审批**：Agent 画（结构提案），用户验收后才落库；Agent 不做布局（位置由前端自动排开）。

| #    | 功能                           | 产品要求                                                                                                                                                                                                                                                                                                                        |
| ---- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M8-1 | 画布读取（read_canvas）        | Agent 按画布 id 读取单张画布结构：元素（标题/类型/所属组）、连线（方向/标签/样式）、引用理解标题；正文默认不返回（token 预算）                                                                                                                                                                                                  |
| M8-2 | 画布列表（list_canvas）        | Agent 枚举画布（可选标题关键词过滤 + limit）；用于「review 项目下所有画布」等盘点场景（list + 逐个 read 组合）                                                                                                                                                                                                                  |
| M8-3 | 画布搜索（search）             | Agent 发现定位：`{ query?, understandingId?, limit? }`。`query` = 1-5 词自由文本，匹配画布标题/元素标题/文本卡内容/连线标签/组名/引用理解标题（正文后置），大小写不敏感、拆词任一命中（OR，发现导向）；`understandingId` = 单个反向查询（哪些画布引用了该理解）；返回画布 + 命中片段（snippet + reason），便于 Agent 判断相关性 |
| M8-4 | 画布写（create/update/delete） | Agent 可新建 / 修改 / 删除画布，**内容级**（增元素、连线、分组、改内容）；全部经用户审批（Agent 画、用户验收）；`update_canvas` 参数在服务端设计文档定义                                                                                                                                                                        |
| M8-5 | 画布展示（draft-preview）      | Agent 的结构提案以 canvas draft 块在消息内联渲染（只读小画布，mermaid 式——输出即渲染、纯展示、不写入）；用户在此诊断，然后「应用 / 修改 / 拒绝」                                                                                                                                                                                |
| M8-6 | 画布引用                       | Agent 回答可引用画布（`[[cv:<id>]]`，与其他实体同一引用体系）；点击不跳路由，打开只读 Modal 展示画布元素（复用同一渲染组件）                                                                                                                                                                                                    |
| M8-7 | 成果可见性（artifact panel）   | 每个对话提供 artifact panel，聚合本对话**已落地**的产出（approve 并保存的 understanding / 新建的 context / sketch 应用后的 canvas）；pending 提案留在消息流（进行时），panel 只显示已落地（完成时）；UX/UI 待调研                                                                                                               |
| M8-8 | 理解结构位置                   | `understanding_get` 与理解详情返回 `referencedByCanvases: [{ id, title }]`——Agent 与用户都能看到该理解出现在哪些心智结构（与 M6-6 共用数据）                                                                                                                                                                                    |

### 版本边界（本版不做）

- 多人协作、评论、投票（本地单机应用）。
- AI 自动生成内容 / 自动连线（违背"关系来自用户显式标记"）。
- 自由画笔 / 手绘。
- 参考线对齐、撤销 / 重做、floating boundary、智能吸附与自动绕障；这些都不是 React Flow Core 默认能力，若采用需作为 Reflecta 自有 Feature 单独定义。
- 画布导入导出除 PNG 外的格式（如 JSON 交换）。
